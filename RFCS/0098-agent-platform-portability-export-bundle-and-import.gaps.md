# RFC 0098 — Gap Register

Open questions, deferred decisions, and "learn-from-implementation" items beyond the in-template Unresolved questions. Each gap has an owner and a resolution path; a gap with no path is promoted to a Risk.

| ID | Section | Question / Missing Input | Owner | Resolution Path | Blocks |
|---|---|---|---|---|---|
| G1 | Proposal §B / Security | Should a bundle be **signed** (RFC 0076 safe-fetch / pack-signing style) when it crosses hosts, and is signature verification mandatory on import? | Security Architect | Recommend: optional detached Ed25519 signature now (additive), mandatory only for cross-host (non-same-host `source.origin`) in a follow-up once the threat is real. Decide before Active. | Active status |
| G2 | Proposal §E (5) | Should imported **executable** behavior default to **staged as RFC 0096 proposals** (review-before-activate) rather than activated directly — i.e., is "import = propose" the safe default? | Security Architect + Spec Architect | Lean yes for executable kinds (agent/pack); make non-executable kinds (templates/roster) direct. Pin per-kind default before Active; depends on RFC 0096 landing. | None (Draft-acceptable) |
| G3 | Proposal §B `items` | Run **history** and **memory** are explicitly out of scope (reusable estate only). Is a future `kinds: ["run-archive","memory"]` extension wanted, with heavier provenance/redaction? | Spec Architect | Keep out of scope here; note as a named future extension. Memory export would need SR-1 + RFC 0057 attribution rules. | None (scoping) |
| G4 | Proposal §C `secretsToRebind` | What is the re-bind UX/contract at the destination — does import return refs the operator binds via RFC 0046, or can a bundle carry a binding *plan* (provider+ref, no value)? | Schema Architect | Define `secretsToRebind` as `[{provider, ref, requiredScopes?}]` (no values); the operator binds via the existing RFC 0046 credential flow post-import. | Schema finalization |
| G5 | Proposal §E (3) idempotency | What makes an item "the same" across hosts so re-import resolves to `skipped`/`updated` not duplicate-create? Source `id`s don't exist at the destination. | Compatibility Architect | Define an idempotency key per kind (e.g. pack `provider.id`+version, agent manifest id, template name+owner); persist a source→target id map. Pin before Active. | Active status |
| G6 | Proposal §C / §E (3) | Topological apply over `dependsOn` + cycle detection (`422`) — confirm the dependency graph is expressible for every kind pair (e.g. a schedule → agent, a roster → agents). | Conformance Architect | Enumerate the legal dependency edges per kind during reference-host impl; conformance scenario covers order + a cycle. | Conformance scenarios |
| G7 | Conformance | Which reference host implements export/import first, and is the **no-secret-values** scenario mandatory for Accepted? (It should be.) | Conformance Architect | Make `no-secret-values` a mandatory Accepted gate; decide example-host vs `openwop-app` reference leg for the rest. | Accepted status |
| G8 | Scope / adapters | Competitor-format adapters (`adapter:openclaw`, …) are explicitly **tooling, not host**. Confirm no normative adapter surface leaks into the spec. | Spec Architect | Keep adapters out of normative text; the RFC standardizes only the openwop-side bundle + import. Note in §Alternatives (already done) and prose. | None (clarity) |
| G9 | Wire / migrate-tenant | Confirm the existing host-private anon→user `migrate-tenant` response can adopt this RFC's `ImportResult` as a superset without breaking its current SPA caller. | Compatibility Architect | Map the legacy `{migrated, runs, workflows, …}` fields onto `ImportResult.counts`; keep them as a compatible subset. Verify against `openwop-app`. | None (migration) |
