# RFC 0118 — Risk Register

Companion to `0118-parallel-subworkflow-fan-out-and-join.md`. Scored Likelihood × Impact (H/M/L). Critical/High risks carry a named mitigation owner and target resolution before the named milestone.

| ID | Risk | Likelihood | Impact | Score | Mitigation | Owner | Status |
|----|------|-----------|--------|-------|------------|-------|--------|
| R1 | **Replay non-determinism.** Parallel children complete in wall-clock order; if `mergeOrder` is not recorded and re-applied, a forked/replayed run reproduces a *different* parent-variable state when two children map to the same output key — a silent correctness break that the wire's replay guarantee (RFC 0041) forbids. | M | H | **High** | §G mandates `mergeOrder` on `core.dispatch.join`; replay re-applies `outputMapping` in that order. Conformance `dispatch-fanout-replay-merge-order.test.ts` is a gating scenario. Author guidance: avoid colliding output keys. | Conformance Architect | Open — scenario must be green for `Accepted` |
| R2 | **Worker-pool exhaustion / self-DoS.** An unbounded fan-out (e.g. 500 `nextWorkerIds`) under `parallel` floods a host's worker pool, starving other runs. | M | H | **High** | §C `maxConcurrency` + advertised `capabilities.dispatch.maxFanOut` ceiling; host MAY enforce its own cap and dispatch in waves (never silently drop). `dispatch-fanout-max-concurrency.test.ts` asserts the wave behavior. | Security Architect | Open |
| R3 | **INTEROP-MATRIX drift.** Hosts adopt `parallel` but stay on suite 1.x, or implement `wait-all` only while advertising all `joinModes` — authors hit registration errors they expected to work. | M | M | **Med** | All scenarios capability-gated on `fanOutSupported`; `fanOutPolicies` / `joinModes` capability descriptors let authors detect partial support; a `joinPolicy.mode ∉ joinModes` is a registration `validation_error` (fails honest, not silent). Update INTEROP-MATRIX column in the landing PR. | Compatibility Architect | Open |
| R4 | **`onChildFailure` default surprise.** If the default (`'collect'`) diverges from the single-child `core.subWorkflow` default (`fail-parent`), authors porting a sequential fan-out to parallel get silently different failure handling. | M | M | **Med** | UQ1/G1 forces an explicit maintainer decision in the comment window; whichever default is chosen, document the divergence prominently in `node-packs.md`. | Spec Architect | Open |
| R5 | **Attestation × approval-gate deadlock.** A `wait-all` join where several children carry RFC 0063 `requireApproval` could suspend the parent on multiple concurrent approval interrupts; a host that serializes approvals could deadlock the join. | L | H | **Med** | Confirm RFC 0063 approval interrupts compose with concurrent children (G6); add an interrupt-profiles note that parallel children raise independent approval interrupts the parent surfaces concurrently, not serially. | Security Architect | Open |
| R6 | **Scope creep into §K1/§K2.** Reviewers push to also resolve same-run sibling dispatch or full output-chunk streaming, ballooning the RFC and delaying the campaign-workflow dependency. | M | L | **Low** | Alternatives §5 + UQ3 explicitly fence those out; the RFC resolves §K2 only to the coarse `fanOut`/`join` marker pair. Hold the line in review. | Spec Architect | Open |
| R7 | **Cross-host clock skew in `mergeOrder`.** Concurrent children on different hosts (RFC 0040) terminate in an order the parent host observes via its own clock; a reviewer may read `mergeOrder` as a global timestamp ordering. | L | M | **Low** | Implementation note + UQ4 clarify `mergeOrder` is the *parent host's* observed terminal order (monotonic, single-clock), never child timestamps. | Spec Architect | Open |
