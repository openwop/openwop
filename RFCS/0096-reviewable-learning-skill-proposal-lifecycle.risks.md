# RFC 0096 — Risk Register

Likelihood × Impact (H/M/L). Critical/High risks carry a named mitigation owner.

| ID | Risk | Likelihood | Impact | Score | Mitigation | Owner | Status |
|---|---|---|---|---|---|---|---|
| R1 | **Inertness violation** — a non-`applied` proposal influences run resolution/planning/execution (the synthesizer's draft leaks into behavior before review). This is the whole point of the RFC. | M | H | **High** | §E(1) MUST + a SECURITY invariant `proposal-inert-until-applied` + a conformance scenario asserting a `draft` proposal does not alter a matching run; only `apply` makes the behavior appear. | Security Architect | Open |
| R2 | **Trace-derived secret/PII leak** — synthesized `rationale`/provenance echoes a redacted secret or personal datum read from the source run traces. | M | H | **High** | §E(4) SR-1 redaction MUST + invariant `proposal-no-content-leak` (G6) + content-free events (`proposal.created`/`activated` carry ids only, never artifact body or rationale). | Security Architect | Open |
| R3 | **Activation privilege bypass** — a malicious or low-quality synthesized artifact is activated by an under-privileged principal, installing executable behavior. | M | H | **High** | §E(2) MUST route through RFC 0051 approval gate (role/scope/quorum, audited override) or require the RFC 0049 activation scope for `direct-rbac`; default `approval-gate` (G4). Activated executable artifacts SHOULD also pass RFC 0043 install policy. | Security Architect | Open |
| R4 | **Re-synthesis drift at activation** — `apply` installs a freshly re-synthesized artifact that differs from the reviewed/persisted draft (reviewer approved X, system installed Y). | L | H | **Med** | §E(3) MUST install the exact last-persisted `artifact` (no re-synthesis at `apply`); conformance scenario byte-matches installed artifact to the persisted draft. | Conformance Architect | Open |
| R5 | **Proposal flooding / catalog noise** — an over-eager synthesizer emits many near-duplicate drafts, overwhelming reviewers (the Curator failure mode). | M | M | **Med** | Optional `duplicationDetection` capability + `duplicateOf` signal (G1); hosts SHOULD coalesce duplicates; reviewers filter by `state`. Non-normative rate guidance. | Spec Architect | Open |
| R6 | **Capability dishonesty** — a host advertises `agents.proposals` but the synthesis/activation path is partial, so a client shows a review queue that can't actually activate. | L | M | **Low** | A host MUST advertise `agents.proposals` only if it serves all §C endpoints incl. `apply`; conformance gates every scenario on the capability; `apply` failure is a legible error, never a fabricated success. | Conformance Architect | Open |
| R7 | **Scope creep into memory** — implementers conflate a proposal (executable artifact) with RFC 0068 memory consolidation (corpus reconciliation), overloading one surface. | L | M | **Low** | Alternatives §3 explicitly separates them; distinct objects, distinct capabilities. Keep the boundary in spec prose. | Spec Architect | Mitigated-by-design |
