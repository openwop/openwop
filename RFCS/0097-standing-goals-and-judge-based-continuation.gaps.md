# RFC 0097 — Gap Register

Open questions, deferred decisions, and "learn-from-implementation" items beyond the in-template Unresolved questions. Each gap has an owner and a resolution path; a gap with no path is promoted to a Risk.

| ID | Section | Question / Missing Input | Owner | Resolution Path | Blocks |
|---|---|---|---|---|---|
| G1 | Proposal §B `progress` | Should a goal decompose into **sub-goals**, or is decomposition left entirely to RFC 0037 multi-agent orchestration? Sub-goals would need their own bounds/judge. | Spec Architect | Out of scope for v1 of this RFC: a goal references `contributingRunIds` only. Revisit as a follow-up if decomposition demand is real. | None (scoping) |
| G2 | Proposal §A `judge: host` | When the judge is opaque (`host`), what is the **minimum verdict shape** `goal.evaluated` must carry so an A2A peer can reason about progress without the objective text? | Schema Architect | Pin a minimal verdict `{satisfied: bool, confidence?: number, runId}` as MUST even for `judge: host`; richer fields optional. Before Active. | Schema diff + interop |
| G3 | Proposal §E (2) `bound-exceeded` | Does crossing a bound auto-escalate (notify a human) or terminate silently with just `goal.closed`? | Spec Architect | Recommend: emit `goal.closed{finalState: bound-exceeded}` always; firing a notification is a host MAY, not a MUST. Confirm before Active. | None (Draft-acceptable) |
| G4 | Proposal §B `bounds` | Confirm the **inlined RFC 0058 bounds object** (the corpus has no standalone `execution-bounds.schema.json` — it is inlined per the floor lock) exposes the three ceilings this RFC relies on — max iterations, accumulated cost, wall-clock deadline. | Schema Architect | Read the inlined RFC 0058 bounds shape; if the cost-ceiling field isn't present, coordinate an additive field with the 0058/0084 authors before Active. | Schema finalization |
| G5 | Proposal §A `judge` / cost | Each completion check is a verifier (RFC 0090) invocation — a real run with real spend. How is judge cost accounted against the goal's `bounds` and RFC 0084 budget? | Compatibility Architect | Decide whether judge invocations count toward `maxIterations`/cost or are metered separately; document in spec prose. Default lean: count toward cost, not iterations. | Active status |
| G6 | Replay / determinism | Does replay determinism hold across a judge-driven continuation loop (the same open question RFC 0068 flagged for consolidation)? A non-deterministic judge makes replay diverge. | Conformance Architect | Carry an explicit Unresolved-questions note (as RFC 0068 did); gate any determinism claim on RFC 0041 replay-under-nondeterminism. | Accepted status |
| G7 | Conformance | Which reference host implements `/goals` first? Needs an RFC 0090 verifier + the scheduler/commitment continuation machinery wired together. | Conformance Architect | Decide example-host vs `openwop-app` reference leg (cf. RFC 0095 precedent). | Accepted status |
| G8 | Boundary vs RFC 0068 | Make the goal-vs-commitment boundary unambiguous in prose so implementers don't build a goal as "a commitment with a repeat flag." | Spec Architect | Add a normative note: a goal *uses* a commitment/schedule/heartbeat as a continuation arm; it is not itself an arm. Cross-link RFC 0068. | None (clarity) |
