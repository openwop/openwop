# RFC 0210 — Gap register

Open design gaps found while authoring RFC 0210 (`exp-only`, the enforced lifetime bound, and the lane → rule binding). Rows are keyed to the RFC; each has an owner and a resolution path.

| ID | Section | Question / Missing Input | Owner | Resolution Path | Blocks |
| --- | --- | --- | --- | --- | --- |
| G1 | §D.10 | `identity.md` §2.2's `anonymous` row has `—` in the `revocation` column, while `auth.schema.json` REQUIRES `revocation` on every lane member. An `anonymous` lane therefore must advertise a value the table does not name; openwop-app advertises `next-request` (`evidence/v2-host-bundles/openwop-workflow-engine.json`). The §D.9 leg leaves `anonymous` unconstrained for exactly this reason, which is a hole in an assertion whose whole point is to have no holes. | Spec Architect | `transferred:spec/v2/core/identity.md` — decide whether `anonymous` takes `next-request` (matching both hosts that have the lane), a new `not-applicable` member, or whether `revocation` becomes conditionally optional for that one lane. Each of the three is a §2.2 edit of a different size; none belongs in this RFC, whose subject is the two JWT lanes. | Nothing in this RFC. The §D.9 leg ships with the exemption named in its own failure message. |
| G2 | §E.11 | `revocation` has **no registry file**. Unlike `spec/v2/errors.json` and `spec/v2/event-codemap.json` it lives inline in the facet schema, so `overview.md` §0's "adding a row to its registry and regenerating" has no literal referent, and the unknown-member tolerance rule attaches to it only by RFC 0197 §A.2 R4's wording "registry-backed **or advertised** enum". §E.11 states the rule explicitly to close that reading; it does not create the file. | Schema Architect | `transferred:spec/v2/facets/auth.schema.json` — either promote `revocation` (and `minimumAssurance`, and `delegationProofs`) to generated registry files, or amend `overview.md` §0 to name advertised-inline enums as a first-class category. The first is tidier and costs a generator; the second is one sentence. Ten members do not obviously justify the first. | Nothing. |
| G3 | Unresolved question 2 | `revocationWindowSeconds` is not conditionally REQUIRED by `auth.schema.json` — only by `identity.md` §2.2's prose and by one suite leg. A lane advertising `exp-and-recheck` with no window is schema-valid today and is caught only by the suite. This RFC does not fix it, for the same reason it keeps the full lane → rule binding out of the schema. | Schema Architect | `transferred:COMPATIBILITY.md` — an `if`/`then` requiring the window on the four windowed rules would retroactively invalidate any committed document that omits it. No committed bundle does today, so the window for adding it is open but not free; it needs the same "measurement at its suite version" disposition RFC 0197 §C used, and belongs with G2's registry decision. | Nothing. |
| G4 | §B.4 / Conformance | The `v2-lane-exp-only-bound` legs need an issuer the suite controls, so it can mint a correctly signed token with an arbitrary `iat`/`exp` pair against a JWKS the host trusts. That is the existing `OPENWOP_TEST_OIDC_ISSUER_URL` harness seam, which means the four §B rows are **harness-gated**, never unaided. A host that does not run the harness records them `inapplicable`. | Conformance Architect | `externally-gated:host-runs-oidc-issuer-harness` — openwop-app (tier-1) or MyndHyve (tier-2) points its `oidc` lane at the suite's issuer for the cut. Both already run a Firebase issuer in production, so the harness lane is additional configuration, not a substitute. | The `Active → Accepted` flip. Nothing before it. |
| G5 | §F.13 | MyndHyve's committed bundle (`evidence/v2-host-bundles/myndhyve.json:488`) advertises `short-lived` / 3600 on `oidc` while the host performs no revocation re-check, and `INTEROP-MATRIX.md` row 18 certifies that bundle for `openwop-discovery-core` **and** `openwop-core-standard`. The §D.9 leg fails that advertisement from the suite minor that ships it, so MyndHyve's next cut is red until the host is corrected. | Steward | `externally-gated:myndhyve-revocation-correction` — `review/handoff-myndhyve-0210.md` states the two admissible corrections (implement `checkRevoked`, or advertise `exp-only` with an enforced window) and the bundle re-cut each owes. RFC 0200's header already requires a MyndHyve deploy of its §A/§B before 0200's first certifying cut: one deploy carries both. | MyndHyve's next cut, and RFC 0200's first certifying cut. Not this RFC's `Active` flip. |
| G6 | §Motivation 2 | openwop-app advertises `openwop-auth-oidc-user-bearer` at v1 (`routes/discovery.ts:436–442`) and omits the `oidc` lane at v2 — a **capability that disappears between majors on a truthful host**. `exp-only` removes the cause, but nothing in the corpus notices a v1 profile with no v2 lane, so the next vocabulary gap produces the same regression silently. | Conformance Architect | `transferred:conformance/src/scenarios` — a leg that cross-checks each advertised v1 auth profile against the v2 lane set and reports (not fails) a profile with no lane. It is a *report* because omitting a lane is legitimate when the host genuinely cannot state a rule — which is the state this RFC exists to end. | Nothing. |
| G7 | §B.7 | The SHOULD ceiling of one hour is a judgement, not a derivation: no upstream document states a maximum access-token lifetime (RFC 9068, OAuth 2.1, MCP and RFC 9728 were read in full for one). One hour is Firebase's ID-token lifetime and the number both hosts would advertise, which makes it a description of current practice rather than a standard. | Spec Architect | `closed` — resolved by declining to invent a MUST ceiling and saying why in the normative text itself (§B.7) rather than leaving the provenance implicit. The row records that the SHOULD's number describes current practice and has no external source; a MUST ceiling, if ever wanted, belongs in a profile predicate carrying its own evidence, not in the vocabulary. | Nothing. The RFC's text already discloses it. |
