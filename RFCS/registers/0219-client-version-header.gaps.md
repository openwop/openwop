# RFC 0219 — Gap register

Open design gaps found while authoring RFC 0219 (the `OpenWOP-Client-Version` request header). Rows are keyed to the RFC. Each has an owner and a resolution path.

| ID | Section | Question / Missing Input | Owner | Resolution Path | Blocks |
| --- | --- | --- | --- | --- | --- |
| G1 | §Compatibility / §C.2 | Two of the three certified hosts read a malformed value as `0.0` and refuse it (`openwop-examples` v2 reference host `router.ts`, openwop-app `protocolVersion.ts`). Under §C.2 both fail the planned `malformed-not-refused` leg. | Conformance Architect | `closed` — 2026-09-27: both hosts fixed and measured before the leg ships. v2 reference (openwop-examples#97) and openwop-app (#4173, production `openwop-app-backend-00773-jq5`) serve `abc` and `1.0abc` and refuse only a well-formed below-floor value. | `Active` |
| G2 | §A / Unresolved question 1 | Whether the value names the corpus release the client implements (this RFC) or a product version (v1's `openwop-sdk/<v>`). | Spec Architect | `closed` — 2026-09-27, decided by the maintainer at `Active` (§Decisions 1): the corpus release, compared on major.minor, not an SDK package version. | `Active` |
| G3 | Unresolved question 3 | RFC 9110 §15.5.22 requires `Upgrade` on every `426`; none of the three hosts sends it and no v2 text names a value. | Spec Architect | `transferred:spec/v2/core/versioning.md` — §1.5 records it as an open gap (2026-09-27, §Decisions 3): the `426` floor departs from RFC 9110 §15.5.22's `Upgrade` MUST and no `Upgrade` value is defined yet. The `426` is RFC 0172 row C5.8's decision and `versioning.md` §1.5 owns it. | Nothing in this RFC. |

| G5 | Unresolved question 2 | The header's meaning on a `/v1/…` path during the overlap. | G8 | §A / upgrade | A browser preflights the new request header. A host whose `Access-Control-Allow-Headers` is an explicit list, and which serves browsers cross-origin, fails every request from a client that sends it.
