# RFC 0198: gap register

This register records the open design gaps found while writing RFC 0198, which maps the MCP server mount to MCP Tasks and defines disconnect semantics. Each row is keyed to the RFC and names an owner and a resolution path. Every row starts with a disposition token (RFC 0166).

| ID | Section | Question / Missing Input | Owner | Resolution Path | Blocks |
| --- | --- | --- | --- | --- | --- |
| G1 | Conformance | No v2 host serves an MCP server mount. v2-reference's committed `mcp` record has no `serverMount`, and MyndHyve and openwop-app advertise no `mcp` at major 2. Every behavioural row is therefore `inapplicable`. | Conformance Architect | `externally-gated:v2-mcp-mount-host` — Two options. (a) openwop-app advertises `mcp.serverMount` at major 2 and adds the Tasks extension and a disconnect→cancel hook to `routes/mcp.ts`. This is the smallest change. (b) v2-reference builds a streamable-HTTP mount. Either way, a production deploy needs the steward's go. | `Accepted` |
| G2 | Compatibility | This RFC depends on RFC 0208, which creates `spec/v2/interop-map.json`, homes the mount (`tools/list`, `tools/call`, `mcp.mrtr`) and sets the incorporation and isolation rules §C.6 and §E.7 cite. | Spec Architect | `closed` — Order the spec PRs so that 0208 lands first. If 0208 is withdrawn, inline §D–§F as a table in `interop.md` (about +90 core words; still under the +300 ceiling) and restate the isolation sentence. | Spec PR |
| G3 | Security | The external-effects rule in §G.12 has no invariant. The candidate is `mcp-request-bound-run-no-orphan`: a run owned by a request never outlives that request's cancellation. Its HTTP half is witnessable (`disconnect-cancels-run`). Its stdio half is not, because a network suite cannot drive stdio. | Security Architect | `externally-gated:v2-mcp-mount-host` — Register the invariant once a host witnesses the HTTP half, with `witness: witnessable-gated` and the stdio half recorded in its `note`. | Nothing |
| G4 | §C.5 | The 128-bit entropy rule binds only runs projected as tasks. `identity.md` §5 fixes the opaque segment's grammar at 16–128 characters of `[A-Za-z0-9._~-]` and says nothing about entropy. A host could therefore mint guessable ids for ordinary runs and random ones for tasked runs, but a run is minted before the host knows whether it will be tasked. In practice every run of an advertising host needs the entropy. | Spec Architect | `transferred:spec/v2/core/identity.md` — Decide in a follow-up whether identity.md §5 should carry the entropy rule for every host-minted tenant-bound id. That would be stricter validation of minted ids, so it needs a safety-fix framing check (COMPATIBILITY §4). Until then §C.5 stands as written, and the suite checks length as a proxy. | Nothing today |
| G5 | Compatibility | V1 disconnect semantics are still undefined. A v1 host that advertises the current MCP profile (`mcp-2026-07-28`) faces the same undefined outcome under the upstream MUST. v1 takes corrections only, and a v1 MUST would need a v1 witness. | Compatibility Architect | `transferred:spec/v1/mcp-integration.md` — Either a v1 Class-3 correction plus a v1 scenario (the upstream MUST makes today's silence a defect), or leave it until v1 end-of-support. Steward decision. | Nothing for v2 |
| G6 | §B.3 | §B.3 removes the server's per-request choice between a task and blocking, and that choice is an upstream MAY. An MCP client that declares the extension but prefers blocking for short calls always receives a task when the run is not terminal at answer time. | Spec Architect | `externally-gated:implementer-feedback` — Watch for implementer feedback. A future additive rule could let a host answer synchronously within an advertised latency bound. No upstream field carries client preference ("clients do not signal task preference on the request itself"). | Nothing |
| G7 | §D | Interrupt kinds that the MRTR `elicitation/create` form projection cannot carry (nested schemas, `refine`/`edit-accept`/`ask`, artifactData; verify-CD C-F4) are also carried in `input_required.inputRequests`. The URL-mode fallback and the credential kind belong to RFC 0199. | Spec Architect | `transferred:rfc-0199` — RFC 0199 amends the `mcp.mrtr` InputRequiredResult row. This RFC's status row references that row and needs no change of its own. | Nothing |
| G8 | §F.11 | The TTL rule is unwitnessable in a bounded suite run. | Conformance Architect | `closed` — Stays unwitnessable. It is recorded in the falsifiability table and is not claimed. | Nothing |
| G9 | §A | `mcp.features[]` stays open in v2, and `extensions` is reused as the signal. A host that lists `extensions` for some other MCP extension, and does not serve Tasks, is still correct: `server/discover` is the authoritative per-extension statement, and `features ∋ extensions` only says to look there. | Conformance Architect | `closed` — The `advertised-via-discover` row asserts only one direction: if Tasks appears in discover, then `features ∋ extensions`. The reverse is not required. | Nothing |
