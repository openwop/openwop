# RFC 0137 — Gap Register

Companion to [`0137-form-content-packs.md`](../0137-form-content-packs.md). Open questions, deferred decisions, and missing inputs beyond the in-template §Unresolved questions. Each gap carries an owner and a resolution path; a gap with no path is promoted to the [risk register](./0137-form-content-packs.risks.md).

| G13 | Security (cross-kind) | **Tool-result trust is unspecified corpus-wide.** The host reports (`FRMD-F1-1`) that sibling agent tools can launder taint: its `crm` / `service-desk` / `priority-matrix` tools return records that the forms submission sinks WROTE — the same attacker-controlled bytes under a different tool id, unfenced. | G14 | Conformance (cross-cutting) | **Three capability-gated behavioral scenarios still soft-skip via a bare `return` instead of `behaviorGate`**, so `OPENWOP_REQUIRE_BEHAVIOR=true` cannot fail on an unadvertised/mis-spelled capability: `artifact-type-pack-install.test.ts`, `artifact-type-store-without-render.test.ts` (both `host.artifactTypes`) and `chat-card-pack-execution.test.ts` (`host.chat.cardPacks`). | G15 | Witness / discovery | **CORRECTED 2026-08-05 — the original entry was wrong and is retained as a correction rather than silently edited.** It recorded the witnessing host as advertising under the deprecated `capabilities` wrapper and therefore resolving only via the migration-window fallback. **That was an over-inference by the steward:** the host had shown a `capabilities["host.forms"]` lookup, and showing a wrapper key does not prove wrapper-EXCLUSIVITY. Verified directly in `openwop-app` `discovery.ts` — `return { ...advertisement, ...advertisement.capabilities }` spreads every family to the document ROOT and retains the wrapper as the deprecated v1.x mirror that `capabilities.md` §"Document-root layout" explicitly permits. The host **satisfies** the document-root MUST, does **not** rely on the fallback, and carries **no v2.0 expiry**. | openwop-app | CLOSED. Only hygiene remains — the same section says a host SHOULD NOT emit the wrapper, so dropping the mirror is cleanup, not conformance debt. The RFC 0137 graduation was never at risk. | Closed |
| G16 | Discovery (cross-cutting) | **RESOLVED 2026-08-05 — the PLAIN family name is canonical; the dotted-only helpers were the outlier.** The steward initially leaned dotted on `host-capabilities.md` §"How a capability is consumed" and its JSON snippets. The reference host supplied the measurement that settles it: `capabilities.schema.json` declares **82 properties and ZERO dotted `host.*` keys**, and — decisively — **five host capabilities are ALREADY declared plainly** (`fs`, `kvStorage`, `tableStorage`, `queueBus`, `scheduling`), each mapping to a `§host.<name>` section (`§host.fs` ↔ `fs`, `§host.kvStorage` ↔ `kvStorage`, …). So the corpus already had an established pattern and the three helpers contradicted it. The `host.` prefix is the capability IDENTIFIER notation (prose `§` headings, pack `peerDependencies`, `error.capability`) — **not** the discovery-document key. | Spec Architect | CLOSED — `readArtifactTypesCap` / `readCardPacksCap` / `readFormContentCap` now read **plain-root → dotted-root → plain-wrapper → dotted-wrapper** (root before wrapper per RFC 0073; the wrapper arms retire at v2.0). Verified against a stub in all four spellings, with an unadvertised host still failing loudly under `OPENWOP_REQUIRE_BEHAVIOR=true`. Widening the READER is not the wire fork this RFC refused for field types — the ambiguity already existed in the corpus, and a schema-following host was silently invisible. Declaring the `host.*` families explicitly in `capabilities.schema.json` remains worthwhile and is left to the RFCs that own them. | Closed |
