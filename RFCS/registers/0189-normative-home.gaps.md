# RFC 0189 — Gap register

Open design gaps discovered while implementing and operating RFC 0189 (the v2 normative-home gate). Keyed to the RFC; each row has an owner and a resolution path.

| ID | Section | Question / Missing Input | Owner | Resolution Path | Blocks |
| --- | --- | --- | --- | --- | --- |
| G1 | §B(c) | `namesKey` is a bare token match, so a family key that is a common English noun is satisfied by prose that merely uses the word. Measured against `spec/v2/core/*.md` with the gate's own predicate: `packs` has an obligation paragraph naming it in **7** documents — including `security-defaults.md` and `versioning.md`, which say nothing about the packs family's contract — and `idempotency` in **7**. Paragraph scope narrowed document scope but does not fix a common noun, and five of the families still undeclared (`packs`, `forms`, `replay`, `interrupt`, `connections`) are common nouns. A contributor under burn-down pressure can resolve `packs` against `security-defaults.md` and the gate will applaud. | Spec Architect | `closed` — RFC 0191. Four syntactic candidates were measured against all eleven declared families and a 24-case known-bad set; ALL FOUR either broke honest declarations (backticks fail five, headings fail six — honest prose names a family in WORDS: \"Connection Packs\", \"Form Content Packs\") or kept the loophole. The numbers were also worse than this row recorded: at 2.11.0 `replay` and `interrupt` each match NINE core documents, `idempotency` eight. Closed with a reciprocal marker instead of a predicate, which makes a false declaration explicit and reviewable rather than impossible — stated as such in RFC 0191 §B rather than claimed as soundness — the two obvious tightenings were measured and both misfire. Requiring the key in **backticks** fails 4 of the 7 families resolved today (`connections`, `toolHooks`, `toolCatalog`, `workflowChainPacks`): honest prose names a family in words ("connection packs"), not as a code token. A two-part variant (backticked anywhere in the document **and** named in the obligation paragraph) still fails `connections` and `workflowChainPacks`, and still resolves `packs` against `security-defaults.md`. Needs a predicate that ties the paragraph to a heading that names the family, sabotage-proven the way §C's three ratchets were — not a drive-by regex change. | Nothing today; it is a soundness ceiling on every future resolution, so it should land before the bulk of the remaining 61 families declare. |
| G2 | §E.2 | 61 families must find v2 homes inside the RFC 0174 §E.2 kernel budget, which `check-core-budget.mjs` reads over `spec/v2/core/*.md` only (non-recursive). At 2.9.0 the budget is **24,836 / 25,000** — 164 words free for 61 families. `spec/v2/ext/**` is a legal home under `homeClass()` and is **not** counted by the budget, and the precedent already exists (`spec/v2/ext/provider-idempotency/README.md` is supporting normative text for the **core** `idempotency` family). Left implicit, 62 authors each discover the escape valve independently and `ext/` silently becomes "core, but unbudgeted" — the 25,000-word cap defeated by directory name. | Spec Architect | `closed` — RFC 0190 §A. The `provider-idempotency` precedent claim in this row was WRONG: no core family declares an `spec/v2/ext/**` home, so the fix had zero retroactive cost. The hole was also worse than filed — an ext-only home needed no `core/` stub at all, and `spec/v2/core/<sub>/x.md` was the same hole one directory shallower. Resolved by making the budget measure what the home gate accepts, rather than by a granularity rule no gate could check — state the rule explicitly: a core family's base contract lives in `spec/v2/core/`; facet-level and operational detail MAY live in a `spec/v2/ext/<topic>/` supporting document co-pointed from `normativeText[]`, outside the kernel budget by design. Or raise the §E.2 budget. Either decision is fine; leaving it undecided is not. | The remaining 62 declarations — the budget as it stands cannot hold them. |
| G3 | §D | The burn-down decays `open` linearly to zero at v1 end-of-support, and `open = v1Dependent + undeclared` — but `v1Carried` families (`toolHooks`, `toolCatalog`) are explicitly tolerated past end-of-support by §D itself, which fails only if their target is deleted or its `Status:` banner changes. Counting a deliberately-tolerated family in a burn-down that must reach zero asks for work the RFC says is not required. | Spec Architect | `closed` — RFC 0190 §C, and the decision went the other way: `open` KEEPS counting `v1Carried`. This row's premise conflated §D's fallback with an exemption. `v1Carried` is hand-written and edited by the declaring PR, so excluding it would make 'add your family to v1Carried' a zero-work way to lower `open`. Closed in the CODE instead — the §D fallback is applied rather than printed, and `v1Carried` must now equal the computed v1-dependent set — decide whether `open` should exclude `v1Carried`. Two rows today; the arithmetic is small, but the schedule's meaning is not. | Nothing; it makes the schedule two families stricter than §D's own fallback. |
| G4 | §B(c) | A markdown TABLE is not one paragraph, but `split(/\n\s*\n/)` treated it as one — so an RFC 2119 keyword ANYWHERE in a table satisfied EVERY family named anywhere in it. Measured: `versioning.md`'s 18-axis disposition table is a single 20-line block; `multiAgent` (row 13) and `schemaVersions` (row 6) were both satisfied by the `MUST` in row 15, which is about `minClientVersion`. Both rows name `events.md` as their owner in their own Owner column, and `events.md` mentions neither family. The gate green-lit both declarations, with the RFC 0191 marker in place — so the marker's "explicit, local and reviewable" guarantee was being read against a reference table where the claim is contradicted three rows away. Eleven of the then-57 undeclared families had a table-only match waiting. | Spec Architect | `closed` — table rows are split into their own units. This is the ONLY tightening of the five measured (RFC 0191's four, plus this) that breaks no honest declaration: it strictly narrows, and none of the resolved families relies on a cross-row match. Sabotage-proved — the `multiAgent`/`schemaVersions` exploit is now refused by name, and all resolved families survive. | Nothing now; it was a live hole under burn-down pressure. |
