# RFC 0096 — Gap Register

Open questions, deferred decisions, and "learn-from-implementation" items beyond the in-template Unresolved questions. Each gap has an owner and a resolution path; a gap with no path is promoted to a Risk.

| ID | Section | Question / Missing Input | Owner | Resolution Path | Blocks |
|---|---|---|---|---|---|
| G1 | Proposal §B `duplicateOf` | Single ref or a ranked near-duplicate cluster (the "Curator" problem)? A single ref under-models a proposal that overlaps several existing artifacts. | Schema Architect | Prototype duplication detection during reference-host impl; if clusters are common, change `duplicateOf` to an array of `{ref, score}` (additive) before Active. | Active status |
| G2 | Proposal §C `PATCH …/revise` | Does `revise` mutate in place (current draft, `updatedAt` bumps) or fork a new versioned `id`? Forking gives an audit trail of revisions but complicates `apply`. | Spec Architect | Decide before Active; if versioned, add a `revisionOf` field. Current lean: mutate in place + rely on `updatedAt` + event log. | Active status |
| G3 | Proposal §D / lifecycle | An `applied` proposal later found harmful — first-class `rollback`, or just the activated artifact's own uninstall path (RFC 0043)? | Compatibility Architect | Recommend reusing the artifact's RFC 0043 uninstall; only add a proposal-level `rollback` if uninstall can't restore prior state. Decide before Active. | None (Draft-acceptable) |
| G4 | Proposal §A `activation` | Is `approval-gate` the safe default and `direct-rbac` an opt-down, or vice-versa? And confirm `capabilities.schema.json` has an `agents` object to extend with `proposals`. | Security Architect + Schema Architect | Default to `approval-gate`; document `direct-rbac` as the explicit lower-friction opt-in. Read `capabilities.schema.json` `agents` shape; mirror exactly. | Schema diff finalization |
| G5 | Proposal §C `apply` | Who validates that the persisted `artifact` is well-formed for its `kind` (an RFC 0003 pack / 0027 template / 0052 job) — at `revise`, at `apply`, or both? | Conformance Architect | Validate against the kind's existing schema at `apply` (MUST) and SHOULD at `revise`; `422` on mismatch. Pin in spec prose before Active. | Conformance scenario `proposal-artifact-schema-valid` |
| G6 | Proposal §E (4) / Security | `rationale` + `provenance.sourceRunIds` must be SR-1 redaction-safe, but the synthesizer reads run traces that *contain* secrets/PII. | G7 | Conformance | Which reference host implements `/proposals` first? `openwop-app` has the synthesis hook; the example hosts do not. | Conformance Architect | Decide whether `Accepted` requires an *example* host or accepts the `openwop-app` reference leg as evidence (cf. RFC 0095 precedent). | Accepted status |
| G8 | Lifecycle / downstream | Once an `applied` proposal becomes a deployable agent, where does RFC 0082 (deployment lifecycle) take over? Avoid two overlapping promotion state machines. | Spec Architect | Document the hand-off: a proposal's `apply` *installs* the artifact; subsequent environment promotion is RFC 0082. Cross-link both RFCs. | None (clarity) |
