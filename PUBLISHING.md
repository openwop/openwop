# Publishing

> **Status:** current release process for this repository.

This repository publishes two npm packages, always together:

| Package | Contents | Source |
| --- | --- | --- |
| `@openwop/openwop-conformance` | The conformance suite and its CLI (`openwop-conformance`). | `conformance/` |
| `@openwop/spec-artifacts` | The contract: `spec/`, `schemas/` and `api/`, with a provenance stamp (`CORPUS-STAMP.json`). | `spec-artifacts/`, generated by `scripts/generate-spec-artifacts.mjs` |

The suite pins `@openwop/spec-artifacts` as an **exact** peer dependency, so the two are one release under two names. They always carry the same version and are always published from the same tag.

Everything else publishes from its own repository:

- SDKs (`@openwop/openwop`, `openwop-client`, `github.com/openwop/openwop-sdks/go/v2`): [`openwop/openwop-sdks`](https://github.com/openwop/openwop-sdks).
- The CLI (`@openwop/cli`): [`openwop/openwop-cli`](https://github.com/openwop/openwop-cli).
- Example and reference hosts: [`openwop/openwop-examples`](https://github.com/openwop/openwop-examples).
- Packs and the registry: [`openwop/openwop-registry`](https://github.com/openwop/openwop-registry).
- The site: [`openwop/openwop-site`](https://github.com/openwop/openwop-site).

The prose, schemas and API documents are also served from this repository and from openwop.dev; `@openwop/spec-artifacts` is the installable copy.

## Versioning alignment

- **One version for both packages.** `@openwop/openwop-conformance` and `@openwop/spec-artifacts` always share a version, and the suite's peer pin names exactly that version.
- **The suite major is the protocol major.** Suite 2.x tests protocol v2. Minors add or correct scenarios for the same major; patches fix assertions or packaging.
- **The corpus tag.** A release is tagged `vX.Y.Z` with the same version. `spec/v2/release.json` records the corpus tag the v2 artifacts derive from (`api/v2/*.yaml` `info.version`, the spec-artifacts stamp).
- **SDKs track the protocol major, not the corpus version.** SDK 2.x implements protocol v2; SDK minors and patches move on their own. A `vX.Y.Z` tag here makes the publish workflow open a reminder issue in `openwop-sdks` so the SDKs can follow a protocol change, but the SDKs keep their own version numbers.
- **Old-major retention.** The last 1.x versions of the suite, the SDKs and the Go module stay installable for 12 months from the v2.0.0 publish (`spec/v2/core/overview.md` §Old-major retention floors; `spec/v2/retention-floors.json`). Never unpublish or retract them inside that window. 1.x fixes, if any, come from the `release/1.x` branch.

## Tags and what they publish

The workflow is [`.github/workflows/openwop-publish.yml`](./.github/workflows/openwop-publish.yml). It fires on three tag forms:

| Tag | Publishes | Use |
| --- | --- | --- |
| `vX.Y.Z` | both packages, then verifies installability | A corpus release. The normal form. |
| `openwop-conformance/vX.Y.Z` | both packages, then verifies installability | A suite fix that has to reach hosts quickly. It publishes spec-artifacts too, because of the exact peer pin. |
| `openwop-spec-artifacts/vX.Y.Z` | `@openwop/spec-artifacts` only | A packaging fix to the contract package alone. |

A pre-release version (`X.Y.Z-rc.N`) publishes under the npm dist-tag `next`, never `latest`.

The jobs, in order:

1. **`validate-tag`** checks the tag format and refuses a tag whose commit is on neither `main` nor `release/1.x`.
2. **`preflight`** runs `npm run openwop:check` on a full-history checkout.
3. **`publish-spec-artifacts`** checks the generated package is current, then publishes it.
4. **`publish-conformance`** runs after spec-artifacts, so the peer exists on the registry before the package that pins it. It builds the CLI and publishes.
5. **`verify-installable`** installs the published suite into an empty directory with no checkout, waits for both packuments, and checks that the installed suite can read its corpus data.
6. **`remind-sdk-release`** (on `vX.Y.Z` only) opens a tracking issue in `openwop-sdks`.

Each publish step first runs `scripts/check-published-suite-identity.mjs`. If the version is already on npm with **identical** contents, the step skips. If it is on npm with **different** contents, the step fails: bump the version.

Publishing uses npm trusted publishing (OIDC) with provenance. No npm token is stored in the repository.

## Version sites

A version bump edits these by hand, each at its exact line. Never run a global `sed` over the lockfile.

1. `conformance/package.json`: `version` and `peerDependencies["@openwop/spec-artifacts"]`.
2. `conformance/package-lock.json`, four lines: the root `version`, `packages[""].version`, the `packages[""].peerDependencies["@openwop/spec-artifacts"]` pin, and the `version` of the `packages["../spec-artifacts"]` entry.
3. `spec-artifacts/package.json`: `version`.
4. `scripts/openwop-check-publish-metadata.sh`: `EXPECTED_CONFORMANCE_VERSION` and `EXPECTED_SPEC_ARTIFACTS_VERSION`.
5. `scripts/check-npm-pack-contents.sh`: the expected conformance version.
6. `conformance/CHANGELOG.md`: the release heading.

At release time, also:

- Set `version`, `corpusTag` and `updated` in `spec/v2/release.json`.
- Add a `## [X.Y.Z] — date — headline` section to `CHANGELOG.md`, moving the `[Unreleased]` lines into it (`scripts/check-changelog-shape.mjs` checks the shape).

Step 5 of the gate (`openwop-check-publish-metadata.sh` and `check-npm-pack-contents.sh`) fails if sites 1–5 disagree.

## Cutting a release

1. **Prepare the release PR.** Make the edits above. Then run the regeneration chain once (see [`CONTRIBUTING.md`](./CONTRIBUTING.md) §"Regenerating derived files and running the gate"), because the corpus tag and version are stamped into generated files. Then run `npm run openwop:check`.
2. **Check the change against a real host.** Run the suite at the base and head of the release against at least one host and compare results requirement by requirement. A release should not turn a passing requirement into a failure unless that is the point of the release.
3. **Merge, then tag the merge commit on `main`.** Confirm the PR is merged and `origin/main` is the merge commit, then:

   ```bash
   git tag -a vX.Y.Z -m vX.Y.Z <merge-commit>
   git push origin vX.Y.Z
   ```

4. **Watch the workflow.** All jobs should pass, including `verify-installable`.
5. **Verify from an empty directory**, never from a checkout, where the peer resolves from the monorepo and hides a missing publish:

   ```bash
   cd "$(mktemp -d)" && npm init -y >/dev/null
   npm install @openwop/openwop-conformance@X.Y.Z @openwop/spec-artifacts@X.Y.Z
   npx openwop-conformance --help
   ```

   If npm reports a peer conflict with packages already in a project, add `--legacy-peer-deps`.

6. **Create the GitHub release** for the tag: `gh release create vX.Y.Z --verify-tag`.

### Pre-publish checklist

- [ ] `npm run openwop:check` passes on the merged tree.
- [ ] All version sites agree, and the tag's version matches them.
- [ ] `CHANGELOG.md` has the release section; `conformance/CHANGELOG.md` has the release heading.
- [ ] Both packages ship `LICENSE` (Apache-2.0); the gate checks the suite's.
- [ ] `ROADMAP.md` still matches what this release ships.

## Rollback

npm does not allow a version to be republished, so a bad release is fixed forward:

1. **Publish a patch** with the fix (`X.Y.Z+1`), using the normal flow.
2. **Deprecate the bad version** with a message pointing at the fix:

   ```bash
   npm deprecate @openwop/openwop-conformance@X.Y.Z "broken: use X.Y.Z+1"
   npm deprecate @openwop/spec-artifacts@X.Y.Z "broken: use X.Y.Z+1"
   ```

3. Don't `npm unpublish`. A host may have pinned the version, and a 1.x version inside the retention window must stay installable.

A security issue in a published version also follows [`SECURITY.md`](./SECURITY.md).
