SQLite's 9 pre-Phase-A failures (`core.dispatch`, `channel-ttl` pruning, conversation-capability refusal, subworkflow `outputMapping`, identity-fixture variable echo, events/poll forward-compat tolerance, and runtime-capabilities `capability_not_provided`) are all closed; the host now passes 100% of applicable default-mode scenarios. Postgres's 1-2 failures are unchanged from 2026-05-11: `webhook-signed-delivery` (flake; passes in isolation) and `pause/resume running→paused→terminal` (fixture-coupled — 30s default delay vs 10s post-resume timeout). None of the failures on either host block the production-profile MUSTs.

Python reference's 53 default-mode failures (re-measured 2026-05-12 against the post-Phase-C-round-2 host) decompose into three categories. **First (unchanged from pre-Phase-C-round-2 baseline):** capability-gated scenarios where the host advertises the underlying fixture but doesn't claim the matching profile — 4 bulk-cancel + 11 interrupt-profile scenarios (approval / clarification / quorum / auth-required / external-event / parent-child cascade) + 3 BYOK + 3 pack-registry + 2 cap-breach + 1 dispatch-loop + 1 conversation-capability-negotiation + 1 append-ordering + 1 channel-ttl-pruning. **Second (Phase C round 2 advertise-but-spec-incomplete):** 5 pause-resume scenarios (host advertises `runs.pauseResume.supported: true` but doesn't yet satisfy the full `:pause`/`:resume` lifecycle — terminal-409 / idempotent-pause / pause-during-suspend-race / resume-non-paused-409 / full-round-trip) + 1 webhook-negative (unregister-unknown returns wrong error code) — Phase C round 2 implemented the new surfaces at advertisement level but the conformance scenarios catch behavior gaps. **Third (pre-existing host gaps the suite catches):** 12 stream-modes scenarios (stream-modes-buffer × 4 + stream-modes-mixed × 4 + stream-modes × 4 — host claims `openwop-stream-sse` + `openwop-stream-poll` but `?bufferMs=` aggregation hint, `?streamMode=` comma-separated subsets, and several mode-specific contracts are unimplemented) + 3 version-negotiation (events/poll past-end tolerance, monotonic sequence assertion, 6-required-RunEventDoc-fields) + 2 subworkflow + 1 highConcurrency + 1 runtime-capabilities + 1 identity-passthrough + 1 route-coverage. None of the failures touch the `openwop-core` scenarios per se — those pass cleanly — but the stream-modes failures are inside the `openwop-stream-*` profile claims and warrant a future honesty pass to either implement the missing behaviors or relax the profile claim. Closing the 53 is a Python-host honesty-cleanup pass (mirroring SQLite's Phase A close-out, plus the new "fix-or-unclaim" surfaces from Phase C round 2). Out of scope for the cross-language portability proof itself.

**Strict-mode posture (`OPENWOP_REQUIRE_BEHAVIOR=true`).** SQLite runs at 669 pass / 10 strict-fail / 32 skip / 30 todo. The 10 strict-fails are intentional honesty opt-outs — the host explicitly does NOT claim `openwop-production`, OAuth2-CC, OIDC, mTLS, auth-scoped discovery, or replay-retention profiles, so `behaviorGate` correctly flips skip→fail under strict mode. Per the host's design these are not bugs; they are the price of advertising only what the host implements. Future strict-mode green requires either implementing those surfaces or relaxing `behaviorGate` to distinguish "host opted out" from "host claims but doesn't deliver." Python reference's strict-mode posture is unmeasured but expected to surface at least 53 strict-fails (the default-mode failures) plus additional behavior-required hard-fails for the Phase C round 2 surfaces it now advertises (`runs.pauseResume.supported: true`, `runs.bulkCancel.supported: true`, `webhooks.supported: true`) — those advertisements unlock strict-mode behavior assertions the host doesn't yet fully satisfy. The honesty-cleanup path is the same as SQLite's Phase A: either implement-to-spec or stop advertising.

## Reading Rows

- **Compatibility profile claim** is derived from `/.well-known/openwop` according to `spec/v1/profiles.md`.
- **Scale claim** follows `spec/v1/scale-profiles.md`.
- **Production profile claim** follows `spec/v1/production-profile.md` and is recorded separately because durability, retention, backpressure, and observability are operational evidence, not discovery-payload predicates.
- **Conformance evidence** should name the suite version, command used, target URL class, and pass/fail/skip counts. Do not include private deployment identifiers, secrets, or internal result paths.
