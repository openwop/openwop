This matrix records public, reproducible compatibility evidence for openwop-compatible hosts. A row is a claim plus evidence: the host advertises a profile set, runs the conformance suite, and links to a result that another implementer can inspect.

⚠️ → 🟢 Discovery-layout divergence — reconciled openwop-side via RFC 0073 (Accepted)

The published agent-manifest-runtime.test.ts helper read discoveryDoc.capabilities.agents.manifestRuntime (nested) — matching the reference host discovery shape and the rest of the conformance suite. MyndHyve serves the agents family at the discovery-document root, which is what capabilities.schema.json actually specifies (agents is a root property; there is no capabilities wrapper; additionalProperties: true) and what capabilities.md §"network handshake" says the schema validates (the full /.well-known/openwop response). So the suite's helper + reference host diverged from the normative schema across the entire agents. family (dispatch / orchestrator / memoryBackends / subRunAttestation / manifestRuntime) — it went unnoticed because additionalProperties: true tolerates the extra nesting. Consequence: the RFC 0070 scenario readManifestRuntimeCap() returned null against MyndHyve → soft-skip (not fail). The investigation found the divergence was broader than 0070: the profile machinery (profiles.ts, multi-agent-capabilities.ts) already read families at the root (schema-correct), while ~40 capability-gated scenarios* read the nested wrapper — so no single host could satisfy both reader families at once.

Resolution — RFC 0073 (Accepted 2026-05-31, openwop-side, NOT a MyndHyve mirror): capabilities.md §"Document-root layout" states the root placement as a normative MUST and marks the capabilities wrapper a deprecated v1.x-window legacy shape; a shared conformance/src/lib/discovery-capabilities.ts accessor reads the document root (root-only as of Phase 4 — see below); the agent-cohort readers (agentRuntime / agentLoop / distillation / subRunAttestation / approval-gate-flow / ai-envelope-shape) are migrated onto it — so the RFC 0070 scenario now grades MyndHyve (root) and the reference hosts (nested mirror) alike, no soft-skip. The primary reference host (apps/.../discovery.ts) emits families at the root (canonical) + a deprecated nested mirror. Phase 2b complete (#279 + the tail): all 78/78 capability-gated conformance scenarios now read via the root-first accessor. Phase 3 complete: all four reference hosts (apps/.../discovery.ts, examples/hosts/{in-memory,sqlite,postgres,python}) emit families at the document root (canonical) + a deprecated nested capabilities mirror for the v1.x window — so the profile machinery (profiles.ts, which reads root) grades them correctly over a live URL, closing the latent honesty gap where root-read profiles (openwop-secrets, openwop-provider-policy) were unverifiable against the previously nested-only shape. Phase 4 complete (v1.x, 2026-05-31 — RFC 0073 → Accepted): the accessor's wrapper-fallback is dropped — the suite reads the document root only and grades a wrapper-only host as non-conformant (root is the MUST). Phase 5 deferred to v2.0: the host-side capabilities mirror + the schema's additionalProperties tolerance retire together (the schema then forbids the wrapper) — paired because both are v1.x backward-compat affordances for laggard clients, and the schema-forbid is a breaking change gated on the v2.0 major.
