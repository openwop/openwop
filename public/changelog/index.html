spec(rfc-0086, rfc-0087): Standing Agent Roster + Agent Org-Chart — filed at Draft (2026-05-30)

Filed two new Draft RFCs that add the named standing agent ("digital-twin employee") layer above the existing manifest/inventory/deployment surface, standardizing an adopter-proven private shape (MyndHyve's AutomationAgent) and adding the distinguishing org-chart layer. Triggers compose RFC 0052 (schedule) + RFC 0083 (durable work-item bridge) — no new WorkflowTrigger.type — and the concrete work surface (a Kanban board) stays a host/vendor extension (the RFC 0083 §E channels-stay-extensions precedent). Additive portfolio projection on the RFC 0072 inventory + two tenant-scoped (RFC 0074) GET /v1/agents/roster[/{id}] reads. Resolves the "manifest is the wrong home for portfolio+triggers" architect finding — the instance is a roster record, not a manifest edit (the RFC 0082 §Alt-3 reasoning).
  • RFC 0087 — Agent Org-Chart (agents.orgChart): a tenant-scoped, descriptive grouping of RFC 0086 roster members into departments + roles with acyclic reportsTo edges and a derived responsibility roll-up, under one load-bearing protocol-tier SECURITY invariant — org-position-no-authority-escalation: an org edge MUST NOT widen toolAllowlist (RFC 0002 §A14), grant an RBAC scope (RFC 0049, the sole authority source, fail-closed), or bypass an approval gate (RFC 0051). Counts: RFC total 85 → 87 / Draft 4 → 6 only — no eventLogSchemaVersion bump, no RunEventType-enum change, no SECURITY-invariant-count change, no prose-spec-count change (all wire surface deferred).   • Phase 3 (RFC 0004) — Agent memory layer — memoryRef resolution, redaction guarantees, host MemoryAdapter contract.
  • Phase 4 (RFC 0005) — Conversation as run primitive — conversation.start / conversation.exchange / conversation.close.
  • Phase 5 (RFC 0006) — Orchestrator-supervisor role — core.orchestrator.supervisor node type.
  • Phase 6 (RFC 0007) — core.dispatch core node — conservative dynamic graph mutation.
