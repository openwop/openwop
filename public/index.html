A common language

OpenWOP defines how clients and hosts start, stream, interrupt, resume, replay, validate, and observe durable AI workflows over REST and SSE, so workflow tooling can move between compliant hosts without a proprietary runtime lock-in.

§ 01 / Specification

Three things the protocol standardizes.

01core

Durable run control

A typed run lifecycle with idempotent creation, suspend / resume, replay / fork, and terminal event ordering that compliant hosts expose consistently.

02policy

Provider policy & BYOK

API scopes, per-run provider routing, BYOK secret resolution, and redaction rules are part of the host contract rather than hidden client convention.

03observability

Trace & cost, end‑to‑end

OpenTelemetry names, W3C trace context, run events, and cost-attribution fields give compliant hosts a shared vocabulary for debugging and operations.

§ 02 / Anatomy

What lives inside an OpenWOP run.

  • A

    Workflow definition

    A declarative graph of nodes, edges, typed channels, reducers, and per-run policy inputs.

  • B

    Run state machine

    Pending → running → waiting → completed / failed / cancelled, with snapshots and ordered events clients can consume.

  • C

    Agent & memory surfaces

    Agent identity, reasoning-event envelopes, conversation interrupts, and memory adapter hooks for hosts that implement the multi-agent extensions.

  • D

    Human checkpoints

    A canonical interrupt shape pauses execution for approval, clarification, refinement, or cancellation, then resumes through the same API contract.

  • E

    Streaming surface

    Run events and message-style updates delivered over Server-Sent Events, with stream modes for dashboards, chat UIs, and debuggers.

  • F

    Node Packs

    Signed bundles of reusable node implementations, with registry operations and host-private marketplaces defined by the v1 spec. The canonical signed registry is live at packs.openwop.dev.

§ 04 / In context

Where it sits, and what it isn't.

Adjacent · MCP

Above the model, not beside it.

Model Context Protocol exposes tools, resources, and prompts to LLM apps. OpenWOP sits at the workflow layer: starting runs, pausing them for humans, streaming events, replaying history, and validating host behavior.

MCP standardizes tool access. OpenWOP standardizes durable workflow execution.
Vs. proprietary

Open by default. Vendor-neutral on purpose.

Agent frameworks are great when one runtime owns the application. OpenWOP is the wire contract between clients, hosts, SDKs, debuggers, and conformance tooling, so product code can depend on a public protocol.

The protocol is portable; each host still owns its runtime guarantees.
§ 05 / Get started

Ten minutes to a running workflow.

Clone the repo, start the in-memory reference host, create a run over HTTP, and inspect the same run through the v1 API. No cloud account, vendor SDK, or managed service required.

Run the quickstart → Reference hosts ↗
~/projects/openwop · zsh ⌘⇧T
# Start the in-memory reference host
$git clone https://github.com/openwop/openwop.git
$cd openwop/examples/hosts/in-memory
$npm install && npm start

# Discover host capabilities
$curl http://127.0.0.1:3737/.well-known/openwop
protocolVersion: 1.0

# Create a conformance fixture run
$curl -s -X POST http://127.0.0.1:3737/v1/runs \
-H 'Authorization: Bearer openwop-inmem-dev-key' \
-H 'Content-Type: application/json' \
-d '{"workflowId":"conformance-noop"}'
▸ runId = run-...
▸ status = pending → completed

# Stream events for the run
$curl -N -H 'Authorization: Bearer openwop-inmem-dev-key'
http://127.0.0.1:3737/v1/runs/run-.../events
event: run.completed

$
