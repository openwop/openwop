# Spec readability pass (openwop)

`spec/v2/**/*.md` renders verbatim at openwop.dev/spec/v2/. Its readers are host implementers, not the RFC process. This skill rewrites prose for them. It is an **editorial** pass: **the set of normative requirements must not change.** A rule that looks wrong gets reported, never "fixed" here.

## Target: $ARGUMENTS

A path (`spec/v2/core/runs.md`), a directory (`spec/v2/ext`), or empty for all of `spec/v2`.

## Step 0 — measure

Work in your own worktree off `origin/main` (CLAUDE.md, "Working in parallel sessions").

```bash
node scripts/check-spec-readability.mjs          # what the gate flags today
```

Then read the target docs as a newcomer would. The gate catches the mechanical failures. It does not catch jargon, narration, or a table that should be a list. Pick the docs that are worst to read, not only the ones the gate names.

## Step 1 — find what parses each doc

Before editing a doc, find every gate that reads its CONTENTS:

```bash
grep -rn "<basename>.md" scripts/*.mjs scripts/*.py conformance/src/coherence/ conformance/scripts/
```

Read each hit that uses a regex, `includes`, a heading split, or a table-row prefix. Preserve exactly what it matches. Known ones, as of 2.42.x:

## Step 2 — rewrite, by these rules

**Hard constraints**

1. Every MUST / MUST NOT / SHOULD / MAY / REQUIRED / RECOMMENDED / OPTIONAL survives with its subject, condition and consequence (status code, error code, field). Split, reorder, deduplicate — never weaken, strengthen, drop or invent.
2. Keep every backticked identifier and HTTP status code, unless it lived only in an aside you removed.
3. Never change an existing heading's text or number: `doc.md §N` and `§"Title"` citations across the repo depend on them. You MAY add lower-level headings. The one exception is stripping an RFC citation from a heading; grep for an inbound `#anchor` first and repoint it.
4. Keep the `> **Status: …**` and `> **Normative home:** …` banner lines. The Status line becomes just `> **Status: Stable.**` (or Draft/Retired).
5. Gate-matched phrases (Step 1) stay verbatim.
6. Generated docs and regions are edited at their generator.
7. The kernel budget (`check-core-budget.mjs`) counts every whitespace token across `spec/v2/core`, including table pipes and bullet dashes. Keep the net word count flat or falling.

**Style**

8. **RFC citations** leave the banner, headings and sentences. Collect them into ONE last line: `*Sources: RFC 0170, RFC 0171.*` (numbers only, ascending). Keep an inline RFC reference only where the RFC is the *sole definition* of something the sentence uses. Write it as a link with an absolute GitHub URL: `[RFC 0041](https://github.com/openwop/openwop/blob/main/RFCS/0041-….md)`. Relative `RFCS/` links break in the `@openwop/spec-artifacts` package. IETF RFCs (RFC 9110, RFC 8785) stay inline.
9. **Paragraphs** carry one idea in at most ~70 words. A paragraph that stacks rules becomes a one-line lead-in plus one rule per bullet, condition first: "On a terminal run, a host MUST …".
10. **Tables** hold short lookup data. A cell with more than ~15 words, or more than one rule, means the table is the wrong shape. Keep a lean table (name → one phrase) and put the rules in bullets below it. Or use bold-term bullets: `- **\`runTimeoutMs\`** — …`.
11. **No history, narration or process.** Cut "was", "used to", "legacy", "since 2.x", "does not exist" lines about removed fields, row and witness counts, and commentary about gates, CI, budgets or RFC process. State what IS. A one-clause rationale is fine.
12. **v1.** Cut v1 comparisons and history. Keep only live rules a v2 host obeys during the overlap. Gather scattered ones into a final `## During the v1 overlap` section, unless an existing heading already holds them. Link cross-doc references: `[identity.md](identity.md) §5`.

`spec/v2/core/runs.md` is the reference example; compare it with `git show 28cc0447:spec/v2/core/runs.md`.

**Scaling.** One doc: do it inline. Many docs: split them across parallel subagents on DISJOINT files in one worktree. Give each agent these rules plus its Step 1 parser list, and have it report per-doc fingerprint deltas with a justification for each. Keep docs that share a gate on the same agent: the push-credential quartet, and the `capabilities`/`overview`/`README` trio.

## Step 3 — verify

```bash
node scripts/spec-fingerprint.mjs [target-substring]   # vs origin/main
node scripts/check-spec-readability.mjs
node scripts/check-core-budget.mjs
```

The fingerprint must show:
- keyword counts unchanged, except where you merged a duplicate statement of one rule or removed an aside (justify each);
- every LOST backticked token justified (aside-only, or now a link);
- no headings CHANGED/REMOVED except stripped RFC parentheticals.

Then run each Step 1 parser for the docs you touched:

```bash
cd conformance && OPENWOP_CONFORMANCE_ROOT=.. npx vitest run --config vitest.coherence.config.ts src/coherence/<name>.test.ts
```

Without `--config vitest.coherence.config.ts`, vitest finds no coherence tests. When `check-spec-readability` reports fewer v1 mentions than its baseline, lower `V1_BASELINE` in the script.

Finally re-read each doc top to bottom. Can an implementer scan it?

## Step 4 — regen, gate, ship

Run the whole regen chain in order, then the gate. See the `pr` skill; the chain is:

```bash
python3 scripts/derive-v2-api.py --write
node scripts/generate-gaps.mjs --write
node scripts/generate-core-standard-manifest.mjs --write
node scripts/generate-assurance-status.mjs --write
node scripts/generate-protocol-status.mjs --write
(cd conformance && node scripts/generate-scenario-majors.mjs --write && node scripts/generate-requirement-registry.mjs --write)
node scripts/generate-spec-artifacts.mjs --write
node scripts/generate-review-packet.mjs --write
node scripts/check-spec-coherence.mjs --write   # twice if a .md was added
npm run openwop:check
```

If `spec-artifacts/CORPUS-STAMP.json` then differs only in `corpusCommit`, restore it: `git checkout -- spec-artifacts/CORPUS-STAMP.json`.

Add one plain `CHANGELOG.md` [Unreleased] line ("editorial; no wire or normative change"). Open the PR with `/pr`. The body lists the fingerprint deltas and their justifications, plus every spec defect you noticed but did not fix. Those defects need an owner, not an editorial pass.

## Step 5 — publish (only when asked)

openwop.dev deploys from `openwop/openwop-site`, which pins a corpus commit and has no push-triggered deploy. After the corpus PR merges:

1. In an `openwop-site` worktree off its `origin/main`: `echo <merge-sha> > OPENWOP_REF`, then `OPENWOP_REF=<sha> bash scripts/provision-corpus.sh`, `OPENWOP_REF=<sha> node scripts/openwop-pin.mjs` and `node scripts/check-homepage-facts.mjs --write`.
2. Commit `OPENWOP_REF` and `openwop-ref.lock` before running `bash scripts/ci-gate.sh`; the gate diffs the lock against the committed copy.
3. Open a PR. `main` requires the "Build + gate" check. Merge it.
4. From the merged site `main`, run `bash scripts/deploy.sh`. It re-runs the gate before shipping.
5. Spot-check a rewritten page with `curl -s https://openwop.dev/spec/v2/core/<doc>.html`.
