# OpenWOP Spec v1 — Changelog

All notable changes to the openwop v1 spec, schemas, OpenAPI/AsyncAPI, conformance suite, and reference SDKs.

Format follows [Keep a Changelog](https://keepachangelog.com/en/1/) loosely. Versions are spec-corpus-wide (one date, multiple artifact updates per row); per-artifact versions live in their respective `package.json` / schema `$id` fields.

> **Status legend** (per [`/governance/spec-status/`](https://openwop.dev/governance/spec-status/)):
> Stable · Stabilizing · Draft · Experimental — see individual doc headers for current state. The legacy `STUB / DRAFT / OUTLINE / FINAL` vocabulary still appears in older releases below; both are valid in the corpus.

> **Package version map.** The version headers below are **spec-corpus** versions, not package versions — each package advances independently on its own per-package release tag. So a corpus version may be skipped here when its number was already consumed by a single-package release, and not every published package version has a corpus row. Notably **there is no corpus `1.1.6`**: that number was taken by a TypeScript-SDK-only npm patch (`@openwop/openwop@1.1.6`, published 2026-05-31, the agent-platform/roster helper catch-up), so the corpus skipped straight to `1.1.7`. A deep-link like `#v1-1-6` therefore has no anchor here by design — the TS SDK's own history lives in [`sdk/typescript/CHANGELOG.md`](https://github.com/openwop/openwop/blob/main/sdk/typescript/CHANGELOG.md) and on npm. Current published per-package versions (as of the `1.1.7` corpus release): `@openwop/openwop` **1.2.0** (npm) · `@openwop/openwop-conformance` **1.18.1** (npm) · `openwop-client` **1.1.7** (PyPI) · `github.com/openwop/openwop/sdk/go` **v1.1.7** (Go modules).

## [Unreleased]

- **RFC 0154 §B — per-section capability gating, because all-on-`supported` forced an overclaim (2026-08-13).** Additive; new `auth.workloadIdentity.delegation` sub-capability and a regated §B leg. **A tier-1 host caught this by asking a question I could not have answered by inspection alone**: *do 0154's scenarios gate each section on its own sub-capability, or all of them on `workloadIdentity.supported`?* They gated all-on-`supported` — which I had written hours earlier without noticing what it implied. **A host that verifies workload identity but does not implement §B delegation had exactly two options**: advertise `workloadIdentity.supported` and hard-fail the §B legs under `OPENWOP_REQUIRE_BEHAVIOR=true`, or advertise nothing and get **no witness for the §A behavior it genuinely has**. Overclaim or silence, with no honest middle — **the same bind RFC 0155 §A names for `openwop-core`, reproduced one capability down and introduced by me while building the machinery to prevent it.** §B now gates on `delegation.supported`. A §A-only posture is honest, advertisable, and witnessable. The sub-capability also carries `maxChainDepth`, because **unbounded delegation is unbounded authority laundering** — each hop is another party the host trusts transitively. The reporting host declined 0154 as a §A.5 witness on grounds that survive this fix (§B–§E are genuinely absent there, and §A.5 requires *every* normative path), but their reasoning corrected two of my assumptions and one of their own, and the question itself was worth more than the answer. **Recorded from their report as a precondition, not a detail:** their `OPENWOP_API_KEY` bearer lane mints a `tenants: ['*']` wildcard principal, and no host can advertise `auth.workloadIdentity` over a lane that does that — it contradicts the R12 identity-is-not-authorization line the capability description itself quotes. Suite `1.95.0 → 1.95.1`.

- **RFC 0154 §A/§B — the workload-identity behavioral witness, and the seam that makes it observable at all (2026-08-13).** Conformance; new `workload-identity-behavior.test.ts` (six capability-gated legs) and `host-sample-test-seams.md` §20. **§A's requirements are invisible from the wire.** A host must cryptographically verify the presented identity, bind it to the request, resolve it to an OpenWOP principal *before* authorization, and fail closed when it cannot — and a normal request either succeeds or 401s, **both of which look identical whether the host verified anything or simply trusted a header**. That invisibility is the whole reason the seam exists, and it is why a missing seam is reported as **`blocked` rather than skipped**: RFC 0148 §A resolves an unobservable requirement to blocked, never to a pass, so **without this endpoint RFC 0154 cannot be certified at all**. Saying that plainly is the point — it is the honest position, not a gap to route around. **The negatives carry the weight.** A host that merely echoes its input satisfies every positive assertion, so only the rejections distinguish a verifier from a passthrough, and each names the specific confusion it rules out: `audience_mismatch` — *an identity minted for another host, accepted here, is how a credential valid elsewhere becomes a credential valid here* (RFC 0147 **R12**); `delegation_expired` — *a delegation without a live expiry is a standing grant, which is not what delegation means*; `sender_constraint_missing` — *without proof-of-possession a bearer credential is replayable by anyone who observed it*, so the host would be asserting who called rather than that the caller held the key. Failures MUST be **non-retriable**: an identity that does not resolve will not resolve on retry, and marking it retriable invites a caller to hammer a failing authorization path. The seam **MUST NOT be a mock that returns a canned principal** — it drives the host's real resolver, because otherwise the witness proves nothing about production. And the framing no assertion can enforce is stated where a reader will meet it: **identity is not authorization**. A `200` means the identity resolved. It never means the caller may act. Suite `1.94.0 → 1.95.0`.

- **RFC 0151 §C–§G — the behavioral witness, which was missing from the SUITE and not only from the hosts (2026-08-13).** Conformance; new `compensation-behavior.test.ts`, five capability-gated legs. **RFC 0147 §A.5 requires that "at least one host MUST execute every normative behavioral path in strict mode" — and RFC 0151 had no behavioral scenario at all**, only a server-free schema check. **A willing host had nothing to run.** That is worth stating plainly rather than folding into a status line: for several turns the remaining blocker was described as *"no host implements this"*, when part of it was that **the evidence-collecting apparatus did not exist either**, and that half was mine to build. Each leg is gated on `compensation.supported` through `behaviorGate`, so it soft-skips against a non-advertising host and **hard-fails under `OPENWOP_REQUIRE_BEHAVIOR=true`** — and records an RFC 0148 §A ledger disposition either way, so an unrun requirement resolves to `blocked` rather than to silence. The legs pin the §C rules that have no other black-box form. **Plan persisted before the first inverse action**: observable only as `compensation.requested` strictly preceding `compensation.started`, and a host that begins unwinding before persisting **cannot resume after a crash — which is precisely when resumption is the thing that matters**. **Descending forward-completion order**: compensating in forward order can release a resource a later inverse action still depends on. **Replay does not re-fire** (§F): a replay that re-executes inverse effects **turns a recovery into a second outage**. **No provider bodies or credentials in events** (§D/§G): these land in the durable log, which is the least revocable place a credential can reach. A missing sample seam fails with a message stating the requirement is **unobservable and therefore `blocked`, not passed** — the RFC 0148 §A default applied at the point where a reader would most want to assume otherwise. Suite `1.93.0 → 1.94.0`.

- **RFC 0148 §C — the runner emits bundle v2, and the first thing it reports is how little it can classify (2026-08-13).** Conformance tooling; new `--bundle-version <1|2>` on `--certify`, defaulting to `1`. v2 records per-requirement dispositions instead of pass/fail/skip file lists. **The honest limit is the point of the change:** the runner reads vitest's per-**file** outcome and does *not* read the RFC 0148 §A requirement ledger, because scenarios do not yet record into it. So a skipped file **cannot** be split into `skipped` / `inapplicable` / `blocked` here — and §A's rule is that an unclassifiable requirement resolves to **`blocked`**, never to a pass. That is what it emits, with the reason in the `detail` field of every such row. **The consequence is deliberate: a v2 bundle produced today shows a large `blocked` count and therefore does NOT certify.** That is not a defect in the emitter — it is the true state of the evidence, which v1 was structurally unable to represent and so reported as a clean `skipped`. The CLI prints the distinction rather than burying it, so an operator who runs this cannot mistake the blocked rows for skips. Real provenance is computed rather than stubbed: `scenarioManifestSha256` digests the executed scenario set, so a bundle cannot be confused with one produced against a smaller suite, and `targetConfigurationSha256` digests base URL + discovery digest + strict-mode flag per RFC 0147 §A.4, so two runs against differently-configured hosts are distinguishable evidence. `assertionCount` and `witnessSha256` are **omitted rather than fabricated** — the runner does not have per-assertion counts, and writing a plausible number would be exactly the lie the field exists to expose. v1 remains the default so no existing consumer changes shape. Verified by assembling the emitter's exact output shape and validating it against `certification-bundle-v2.schema.json`. Suite `1.92.0 → 1.93.0`.

- **RFC 0147 §A.9 — the documentation sweep, which found an inconsistency this program created (2026-08-13).** Documentation; `INTEROP-MATRIX.md`, `docs/KNOWN-LIMITS.md`, and the self-audit row. §A.9 requires each workstream to update the interop matrix, known-limits, and protocol status when its evidence changes. `docs/PROTOCOL-STATUS.md` is generated and gated, so it was already current; the other two were not, and the sweep turned up a **live contradiction between two files, introduced by this program**. `INTEROP-MATRIX.md` still listed the in-memory host as claiming `openwop-stream-sse` and `openwop-stream-poll` **after those claims were withdrawn from its certification bundle** (openwop-examples#12) for being contradicted by its own `results.failed`. Fixing the bundle without the matrix left the corpus **asserting in one file what it had retracted in another** — the same class of defect as the `replay.md` staleness RFC 0150 §B introduced and did not catch, and a reminder that a correction is not complete until every artifact that repeats the claim has been found. The row now names the two retained claims and states that **both are discovery-payload-only**, so neither says anything about runtime behavior (RFC 0155 §A). `KNOWN-LIMITS.md` gains a section recording what this repository **cannot** close: the §A.5 host witness for RFCs 0151–0154, the external security audit, the second maintainer (Critical risk **R14**, which "closes when a person volunteers"), and a Tier-3 host — **four gates that are adoption and governance events rather than work items** — plus both currently-violated invariants and the fact that **no extension can reach `stable`** while §C gates it on a Tier-3 implementation. **Deliberately not swept:** the SQLite, Python, and Postgres host rows, whose profile claims derive from per-host `conformance.md` files this program did not audit. Asserting them corrected without checking would be precisely the overclaim the self-audit exists to catch, so they are named as unswept instead. §A.9 moves from *partially satisfied* to *satisfied for this program's evidence*; the audit tally is now two violations, two partial, two unsatisfied, four satisfied.

- **RFC 0148 §C — certification bundle v2, which can express "we could not check" (2026-08-13).** Additive; new `schemas/certification-bundle-v2.schema.json` and `certification-bundle-v2.test.ts`. v1 recorded `{passed, failed, skipped}` as scenario-**file** lists, and those three words cannot express the distinction this whole program turns on. A file counted as `passed` **whether its assertions ran or its runner returned early** — which is how a gated subtest that 404'd left a green file and a green bundle. And `skipped` flattened **three different claims into one word**: *the operator excluded this*, *the requirement does not apply here*, and *we could not check*. The first two are certifiable; the third invalidates the claim — and v1 had no way to say it. v2 replaces the lists with per-requirement dispositions from §A and adds the counts §A.4 requires, so a reader can tell a thorough run from a thin one without re-running it. Two properties are load-bearing. **`blocked` is a required total**: `blocked: 0` *asserted* is a different claim from `blocked` *unstated*, an omitted total is indistinguishable from zero, and the one total that invalidates a certification is the one most worth omitting. **`assertionCount` makes a vacuous pass visible** — and the schema **deliberately still admits** `executed-pass` with `assertionCount: 0`, because forbidding it would only move the lie one field over (a generator could write `1`), whereas putting the number *in the artifact* lets a reader or a downstream verifier see a pass that executed nothing **without re-running the suite**. That is the honest limit of what a schema buys here, and the test that covers it asserts validity rather than rejection so the reasoning cannot be mistaken later for an oversight. Also: `claimedProfiles` is constrained to canonical `openwop-*` IDs with deprecated aliases confined to `aliases` (RFC 0155 §E) — a badge substantiated by a name that no longer means what it did is the `openwop-core` ambiguity in bundle form; and `scenarioManifestSha256` / `targetConfigurationSha256` are required, because without them a bundle cannot be distinguished from one produced against a smaller suite or a differently-configured host. Sabotage-verified: dropping `blocked` from `required` and removing `minItems` on the requirement list red two legs. **Carried:** the runner does not yet emit v2, and no host publishes one. Suite `1.91.0 → 1.92.0`.

- **RFC 0154 §A/§B — workload identity and delegation, shape only (2026-08-13).** Additive; new `schemas/workload-identity.schema.json`, an `auth.workloadIdentity` capability, and `workload-identity-profile.test.ts`. **§A's real requirements are behavioral** — cryptographically verify the presented identity, bind it to the request, resolve it to an OpenWOP principal *before* authorization, and fail closed when unresolvable — and **a schema demonstrates none of them.** RFC 0147 §A.5 forbids `Accepted` on this evidence, and a final leg asserts both the behavioral and external-audit acceptance items stay unticked and annotated. **What a schema can do is make the dangerous shape unrepresentable**, and that is what this enforces. The governing rule is negative: **raw certificates, tokens, proofs, and credentials MUST NOT enter these objects.** `subject` is an opaque identifier; `proofRef` and `thumbprintRef` are **pattern-constrained digest references**, so a JWT or a raw key cannot be pasted in and still validate. A verified identity is a fact about a *completed verification*, not a container for the material that proved it — and it matters here more than in most schemas because these objects are projected into **events, spans, and audit records**, which are the three places credential material must never reach (`SECURITY/threat-model-secret-leakage.md`). `audience` is required on a delegation because an identity minted for somewhere else, accepted here, is exactly how a credential valid elsewhere becomes a credential valid here — the confused-deputy path RFC 0147 **R12** names. And **identity is not authorization** is the one rule a schema cannot enforce at all, which is why it is stated in the schema description rather than pretended into a constraint: knowing which workload called says nothing about what it may do, and tenant, audience, and policy are re-evaluated at every boundary regardless. The `schemes` enum is closed because **an unrecognized scheme is a verification path nobody implemented**, and accepting the *name* without the verification is precisely the failure the profile exists to prevent. Sabotage-verified: opening `additionalProperties` and dropping the digest pattern red two legs. Caught in passing by the corpus gate — `schemas/README.md` must index every schema exactly once, and the new file was missing until the gate said so. **Carried:** §C OTel mapping, §D provenance attestations (which span `openwop-sdks` and `openwop-registry`), and every behavioral scenario. Suite `1.90.0 → 1.91.0`.

- **RFC 0152 + RFC 0153 §A — versioned A2A and MCP composition, shape only (2026-08-12).** Additive; `protocolVersions`, `preferredVersion`, and `profiles` on the `a2a` and `mcp` capability families, plus a closed `features` list on `mcp`, and `versioned-composition-profiles.test.ts`. **They land together because they address the same defect:** `supported: true` with no version is **a claim a peer cannot negotiate against**. It asserts the host speaks *some* A2A or *some* MCP. Two hosts can both advertise it, share no revision, and discover that only when a call fails — **and the failure surfaces at the peer, not at the handshake that was supposed to prevent it.** Versioning the advertisement moves the disagreement to the one place both sides are already looking. Two shape choices worth keeping: **MCP versions are date-patterned rather than free strings**, because MCP revisions *are* dates and accepting `latest` or `2026-7-28` would let two hosts disagree about which revision they share while both validate; and **the MCP feature list is closed**, because an unrecognized feature name is indistinguishable from a typo and a peer that silently ignores one has negotiated a capability neither side implements. Naming the legacy profile explicitly (`a2a-0.3-legacy`) is the same idea applied to deprecation — **a deprecation you can see is one you can time-bound**, where a bare `supported: true` hides it. **Shape only, and the file says so in its own header:** nothing here contacts a peer, so this is not evidence of interop with any A2A 1.0 or MCP 2026-07-28 implementation, and RFC 0147 §A.5 forbids `Accepted` on that basis. A final leg asserts both RFCs keep their upstream-peer acceptance items unticked and annotated, because **interop is precisely the thing a schema cannot demonstrate**. **A first draft had its negative legs passing for the wrong reason:** the `a2a` family independently requires `agentCardUrl` (RFC 0100 — it must GET-resolve credential-less), so fixtures omitting it were rejected for the missing card URL rather than the version defect each leg names. Green for a reason unrelated to the assertion is the vacuity pattern this program exists to close, committed inside a test written to prevent it; every fixture now carries the field. Sabotage-verified: removing `minItems` reds the empty-list leg, and loosening the MCP pattern to a free string reds the date-form leg. Suite `1.89.0 → 1.90.0`.

- **RFC 0151 §A/§B — the compensation profile, shape only and labelled as such (2026-08-12).** Additive; new `compensation` capability family and node-level `compensation` declaration, plus `compensation-profile.test.ts`. **What this establishes is stated in the conformance file itself, not buried in a register:** the schemas admit exactly the shapes §A and §B describe and reject the ones they forbid. That is **shape-only evidence**. It is *not* evidence that any host orders an unwind correctly, persists a plan before executing its first inverse action, or resumes one after a crash — and **RFC 0147 §A.5 forbids `Accepted` on shape-only evidence for a behavioral requirement**. A final leg asserts 0151's behavioral acceptance item stays unticked and annotated, so **reading the conformance suite alone cannot leave a different impression than reading the RFC**; a file that verifies structure while its RFC claims behavior is how "green suite" and "working protocol" come apart. Three design constraints the schema encodes rather than merely documents: **compensation is a second effect, not an undo** — it can fail, can be partially applied, and can itself be harmful (RFC 0147 R9), which is why `requiresApproval` exists and the extension is security-tier high; **inputs derive from recorded facts**, because §B forbids prompt or model regeneration from constructing a compensation input during replay — an inverse built from a re-inferred value is not the inverse of what was actually done; and **`nodeTypeId` MUST resolve at registration**, so an unwind cannot fail on a typo first discovered during a failure, which is the worst possible moment to learn of one. `orderingModels` is a closed enum of the two named models, and `profileVersion` is pattern-constrained because §C makes it part of the inverse-action identity — an unconstrained string there would let two hosts mint colliding identities under different ordering rules. Sabotage-verified: opening `additionalProperties` on the declaration reds the closed-shape leg. **Carried, and it is the whole behavioral half:** §C lifecycle, §D events, and the reverse-unwind / retry / crash / partial-manual / approval / replay / isolation scenarios, none of which can be written without a host that implements them. Suite `1.88.0 → 1.89.0`.

- **RFC 0147 §A.10 — the program audits itself, and finds two violations (2026-08-12).** Governance record; new `docs/RFC-0147-SELF-AUDIT.md` and `rfc-0147-self-audit.test.ts`. §A states ten invariants that "apply to every workstream", and §A.10 forbids using the RFC's existence or partial implementation as evidence its gaps are closed. **A program that audits everything except itself has the same defect it was written to fix, one level up.** Two rows come back **VIOLATED**. **§A.5** — "a child RFC MUST NOT reach `Accepted` using shape-only evidence for a behavioral requirement; at least one host MUST execute every normative behavioral path in strict mode" — RFCs 0151/0152/0153/0154 are `Accepted` with **no evidence at all**, not merely shape-only: no spec prose, no schema, no conformance, no host. **§A.6** — "a high-risk RFC affecting identity, authorization, isolation, idempotency, replay, external effects, or certification MUST complete the full public comment window; **bootstrap waiver language MUST NOT shorten that window**" — and 0148 (certification), 0150 (idempotency/replay/external effects), 0152, 0153, and 0154 (identity/authorization) all had their windows waived under `MAINTAINERS.md` §"Bootstrap-phase RFC waivers", **which is precisely the mechanism that sentence forbids**. The available technicality is that 0147 was itself `Draft` at the instant of the flip and became `Accepted` in the same change, so §A.6 arguably was not yet in force. **That argument is recorded and deliberately not relied upon** — reading the program's own partial state in whichever direction is convenient is exactly the shape §A.10 exists to forbid. The steward waived knowingly and holds that authority; what §A.6 costs is not the decision but **the claim** — those five RFCs cannot be cited as having cleared a high-risk review window, because they did not. Also recorded: §A.1's freeze **still binds** (Critical risk R14, "no independent maintainers volunteer", is open) but does **not** block 0151–0154, since the summary frames the freeze as protecting the program *"while nine named workstreams repair"* the corpus and those RFCs **are** workstreams 4–6; §A.2 (five reviews) and §A.8 (example extraction) are unsatisfied; §A.4 and §A.9 partial. **The gate deliberately does not assert compliance.** It asserts every invariant carries an explicit disposition — including the adverse ones — because making it fail on a violation would create pressure to delete the row rather than fix the program, the failure RFC 0149 §D measured when it declined to ship a gate firing 69 times on its first run. Sabotage-verified in both directions: replacing `VIOLATED` with `satisfied` reds, and deleting the §A.6 section reds. **Bottom line, stated in the corpus rather than left to be discovered: the exit criteria in RFC 0147 are not met**, and three of the remaining gates — external audit, second maintainer, Tier-3 host — cannot be closed by work in this repository. Suite `1.87.0 → 1.88.0`.

- **RFC 0155 §B/§C — the core-standard manifest and the extension registry (2026-08-12).** Additive; new `spec/v1/core-standard-manifest.json`, `spec/v1/extensions.json`, `scripts/generate-core-standard-manifest.mjs`, and a check wired into `openwop:check`. **§B's value is the sentence after the inventory**: *"prose and code profile definitions MUST be generated from or checked against this manifest."* Three places describe the `openwop-core-standard` floor independently — the profile prose, `PROFILE_FLOOR_SCENARIOS`, and the requirement registry — and before this they could only be **assumed** to agree. They did not: `PROFILE_FLOOR_SCENARIOS` was an incomplete transcription of `profiles.md`, and every profile it omitted verified as floor-proven **against nothing** (RFC 0148 §C). A manifest with a parity gate is the mechanism that would have caught it. So the manifest is **derived and never hand-listed** — a hand-listed manifest drifts the moment the corpus moves and then asserts the drift *with a digest attached*, which is worse than no manifest because it looks authoritative. It also carries **no timestamp**, deliberately: a generated file that changes on every run cannot be parity-gated, and a digest over a moving value proves nothing. §C's registry carries six closed records, backfilled from each RFC's own status and its landed/carried annotations rather than authored fresh. **Every record is `draft`, and nothing in this corpus can currently be `stable`** — §C gates stable on at least one Tier-3 implementation and none exists, the `ROADMAP.md` tripwire never having fired. That ceiling is **recorded rather than worked around**: it is a fact about adoption, not about the maturity of the work, and promoting anything past it would be exactly the overclaim RFC 0147 §A bans. **A first draft of this change marked `openwop-effect-identity-v2` stable with a null `evidenceTier`** — richest evidence in the corpus, and still short of §C's bar — which would have shipped a registry that failed its own gate. Corrected to `draft` before landing; **landing a knowingly-red gate would have been worse than the disease it treats.** New `core-manifest-and-extension-registry.test.ts`, eight always-on server-free legs including a non-vacuity guard. Sabotage-verified on both halves: dropping a floor scenario from the manifest reds the parity leg, and marking any extension `stable` without an evidence tier reds the overclaim leg. **Carried:** the registry is not complete for the whole corpus — it covers the extensions the RFC 0147 program introduces or names, and **unlisted means uncovered rather than compliant**, the same distinction RFC 0148 §C drew between an empty floor and an unwritten one. Suite `1.86.0 → 1.87.0`.

- **RFC 0150 §C — the golden vectors, and a vacuity in the gate written to catch vacuity (2026-08-12).** Conformance artifact; new `conformance/vectors/semantic-request-digest-v2.json` (eleven vectors) and `semantic-digest-vectors.test.ts`. §C's acceptance criterion is that **TypeScript, Python, and Go compute the same digest**, and prose cannot deliver that: three independent readings of *"canonicalize via JCS and hash"* is precisely how three implementations diverge, and the divergence is invisible until two hosts replay the same run and get different cache keys. So the vectors are the contract — each carries its `input`, the exact JCS `canonical` preimage, and the `digest`, so a failing implementation can diff the preimage instead of staring at two hashes. **Several vectors are pairs whose relationship is the actual requirement**: tools sorted vs reversed MUST agree (order is not semantic); message order reversed MUST NOT (order is); and the two Unicode forms of `é` MUST NOT, because JCS does not apply NFC. **That last pair is the one that earns its place** — an implementer who adds NFC "to be safe" makes those two collide while *every other vector still passes*, so a suite checking only individual digests goes green on an implementation that has silently lost cross-host byte agreement. **And the first draft of this gate had exactly the bug it was written to catch.** The relationship legs called a helper that returned the **stored** digest, so `expect(digest(a)).not.toBe(digest(b))` compared two constants out of the same file: it validated that the vector *set* was internally distinct and would have passed unchanged against a broken implementation. The NFC sabotage was caught by the per-vector reproduction leg — while the leg named for it could not have failed. Found by running the sabotage and reading *which* legs fired rather than accepting that one did. Now recomputes from `input`; sabotage reddens two legs where it previously reddened one. **Carried, and now genuinely the only remainder for §C:** the Python and Go implementations, which live in `openwop-sdks` and consume this file rather than re-reading the prose. Suite `1.85.0 → 1.86.0`.

- **RFC 0150 §C — the digest excluded the fields that decide the answer (2026-08-12).** **Safety-fix** per `COMPATIBILITY.md` §3; `replay.md` cache-key recipe v1 → **v2**. Three defects, and the third is mine. **(1) The exclusion list forbade exactly what §C requires.** §A read: *"Fields NOT in this set MUST NOT influence the cache key — including but not limited to: `max_tokens`, `stop`, … `seed`."* All three **change the completion**: two requests differing only in `stop` produce different text, `seed` exists to change output, and the output bound decides whether a response is truncated. Keying them identically does not cause a cache *miss* — it causes a **wrong hit**, returning a response the caller never asked for, and doing so **deterministically rather than intermittently**, which is the harder failure to notice. `stream`, `metadata`, and `user` stay excluded because they cannot alter the completion; the test is whether a field can change what the model returns, not whether it rides along in the HTTP request. **(2) It prescribed a normalization JCS does not perform.** Step 2 said canonicalize "via RFC 8785 JCS", then told hosts without JCS to emit "UTF-8 NFC for all strings". **JCS does not apply NFC.** So the two routes offered in a single sentence produced **different bytes for the same input** whenever a string was not already normalized — and cross-host byte agreement is precisely what §D asserts as a normative invariant. Both hosts would have been following the spec. **(3) It quoted a Layer-2 formula that no longer exists** — the `attempt`-bearing composition RFC 0150 §B retired as a safety-fix. `idempotency.md` went to v1.4; `replay.md` was left citing v1.1. **That is a cross-document staleness the §B change introduced and did not catch**, and a reader following it would have rebuilt the exact defect §B removed while believing they were following the spec. v2 stamps the canonical object `recipe: "openwop-semantic-request-v2"` so a digest computed under retired rules is **distinguishable rather than silently comparable**, and requires unknown provider options to be carried in a closed namespaced `providerOptions` — *"silently dropping them is nonconformant"*, because a dropped option that alters output is indistinguishable from one never set. **The gate reads normative text only, excluding blockquotes**, because the document deliberately quotes the rules it retires so a reader can see what changed — and a substring search cannot otherwise tell a live rule from a quoted-and-retired one (same carve-out shape as RFC 0149 §B's pre-0073 exemption). Two guards keep that narrow: the filter must retain >70% of the file, and **sabotage-verified that reintroducing a retired rule in normative voice still reds** while the quoted history does not. New `semantic-digest-v2.test.ts`, six always-on server-free legs; red-before-green on five. **Carried:** the cross-language golden vectors, which live in `openwop-sdks`. Suite `1.84.0 → 1.85.0`.

### Multi-Agent Shift (Phases 1-6 landed by freeze)

- **Phase 1 (RFC 0002)** — Agent identity (`AgentRef`), agent reasoning + tool + handoff event family, confidence-escalation contract, `message` reducer.
- **Phase 2 (RFC 0003)** — Agent capability discovery on `/.well-known/openwop` + `pack.json` `agents[]` extension.
- **Phase 3 (RFC 0004)** — Agent memory layer — `memoryRef` resolution, redaction guarantees, host `MemoryAdapter` contract.
- **Phase 4 (RFC 0005)** — Conversation as run primitive — `conversation.start` / `conversation.exchange` / `conversation.close`.
- **Phase 5 (RFC 0006)** — Orchestrator-supervisor role — `core.orchestrator.supervisor` node type.
- **Phase 6 (RFC 0007)** — `core.dispatch` core node — conservative dynamic graph mutation.
