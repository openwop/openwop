### Host + Conformance — RFC 0028 §B prompt-pack boot-time install (2026-05-20)

### RFC 0033 (Draft → Active) — envelope-completion contract (truncation vs schema-violation retry routing) (2026-05-20)

Spec text + error-code work for stage 3-continued (final) of the envelope LLM-contract-hardening track (RFCs 0030–0033). Closes spec gap E5 from `ai-envelope.md` §"Open spec gaps" (refusal-mode interaction with retry policies — worked example). Layers retry-routing semantics on top of RFC 0032's event vocabulary; introduces NO new event types. Capability advertisement (`envelopes.reliability.completion`) landed in the RFC 0032 schema batch since 0033 depends on 0032's event vocabulary structurally. Promotion under the bootstrap-phase steward waiver per the RFC 0021–0032 precedent. Remaining acceptance criteria (2 conformance scenarios, reference-host emission, spec gap E5 closure annotation) define the path to `Accepted`.

- **`spec/v1/ai-envelope.md`** — extended with §"Envelope-completion criteria" between §"Production flow" and §"Replay determinism". Normates: (1) completion criteria — an envelope is complete only when both clean stop AND payload-validates hold; (2) truncation retry path — MAY retry with INCREASED output budget (RECOMMENDED 2× multiplier per `truncationBudgetMultiplier`); MUST NOT include corrective schema fragment; counts against `limits.schemaRounds`; exhaustion → `envelope_truncation_unrecoverable`; (3) schema-violation retry path — MAY retry with host-authored corrective system fragment (not from model output); MUST NOT increase output budget; counts against `limits.schemaRounds`; exhaustion → `envelope_payload_invalid`; (4) refusal path — MUST NOT retry (circumvention concern); fails with `envelope_refused_by_provider`; (5) recovery path — internal to parsing, no retry consumed. Priority rule when truncation + schema-violation both fail: treat as truncation (output budget is upstream cause).
- **`spec/v1/observability.md`** — §"Envelope-completion retry routing (RFC 0033)" landed in the RFC 0032 batch as cross-track observability documentation. Summarizes the routing distinction; cross-references the two new error codes.
- **`spec/v1/rest-endpoints.md`** — §"Common error codes" gains two new codes: `envelope_truncation_unrecoverable` (truncation retry budget exhausted while failure mode remained truncation; paired with `envelope.retry.exhausted { finalReason: "truncation" }` + `cap.breached`; distinct from `envelope_payload_invalid` which covers the schema-violation path) and `envelope_refused_by_provider` (provider returned explicit refusal; MUST NOT retry; error `message` MUST NOT echo refusal text per SECURITY invariant `envelope-refusal-no-prompt-leak`).
- **`schemas/capabilities.schema.json`** — `envelopes.reliability.completion` sub-block landed in the RFC 0032 batch. Required `distinguishesTruncation: boolean`; optional `truncationBudgetMultiplier: 1..8` (default 2; informational).
- **`schemas/run-event.schema.json` + `schemas/run-event-payloads.schema.json`** — REUSES the six RFC 0032 envelope-reliability event types unchanged. This RFC introduces NO new event types; the retry-routing semantics layer on top of RFC 0032's existing vocabulary.
- **`RFCS/0033-envelope-completion-contract.md`** — status `Draft` → `Active`; status-history block records the promotion + the remaining `Active → Accepted` path. Notes spec gap E5 closure pending follow-up doc-prose pass.

Compatibility: **additive** per `COMPATIBILITY.md §2.1 + §4`. Two new error codes (no existing code changed); two new MUSTs (no existing MUST relaxed) — both MUSTs introduced in previously-undefined behavior space (the retry-routing distinction was silent in v1.1) and gated on `capabilities.envelopes.reliability.completion.distinguishesTruncation: true`. Hosts that don't advertise retain their legacy retry-routing behavior. Existing `envelope_payload_invalid` code unchanged (still the schema-violation-retry-exhaustion code).

### RFC 0032 (Draft → Active) — envelope-reliability run-event vocabulary + line-448 scope clarification (2026-05-20)

Spec text + wire-shape work for stage 3 of the envelope LLM-contract-hardening track (RFCs 0030–0033). Carries the **central design decision** of the track: the `ai-envelope.md` §"Run event log integration" line-448 MUST NOT is **scope-clarified** (not relaxed) — "envelope-specific events" is read as *per-envelope-kind routing events* (which would create a parallel routing surface and remain FORBIDDEN), NOT as *cross-kind operational events* (retry, refusal, truncation, capability substitution, prompt composition, provider usage). The cross-kind operational allowance was always implicit in existing precedent (RFCs 0026 / 0027 / 0029 / 0031 shipped under the same interpretation); RFC 0032 §A makes the precedent explicit so future RFCs that extend `RunEventType` for operational concerns don't get blocked. Promotion under the bootstrap-phase steward waiver per the RFC 0021–0031 precedent. Remaining acceptance criteria (6 conformance scenarios, 2 SECURITY invariants `envelope-refusal-no-prompt-leak` + `envelope-recovery-no-content-leak`, INTEROP-MATRIX rows, reference-host emission) define the path to `Accepted`.

- **`spec/v1/ai-envelope.md`** — line-448 prose CLARIFIED per §A. Original FINAL-v1.1 text quoted verbatim; clarified text replaces "envelope-specific events" wording with "per-envelope-kind routing events" + explicitly permits "cross-kind operational events" via RFC. Lists consuming RFCs (0026, 0027, 0029, 0031, 0032) so the precedent is permanent. Classified additive per `COMPATIBILITY.md §4` (scope clarification of previously-undefined behavior; per-kind events remain forbidden after the clarification — NOT a MUST relaxation). New §"Envelope-reliability events" between §"Run event log integration" and §"Wire serialization": documents the six events + tier table + capability-handshake example + `reason` enum extensibility (closed enum + `x-host-*` pattern matching RFC 0031 §B precedent) + trust-boundary + replay determinism + OTel projection cross-reference.
- **`spec/v1/observability.md`** — new §"Envelope-reliability events (RFC 0032)" + §"Envelope-completion retry routing (RFC 0033)" between §"Provider usage events" and §"Open spec gaps". Documents the OTel attribute mapping per event; `envelope.refusal.refusalText` exclusion from OTel by default (private side channel); the two SECURITY invariants with their gate timing; the RFC 0033 truncation-vs-schema-violation retry-routing distinction for cross-reference.

### RFC 0031 (Draft → Active) — envelope variant discrimination + model-capability declarations (2026-05-20)

### RFC 0030 (Draft → Active) — envelope `reasoning` field + Tier-1 structured-output subset (2026-05-20)

Spec text + wire-shape work for the lowest-risk additive entry in the envelope LLM-contract-hardening track (RFCs 0030–0033). Promotion under the bootstrap-phase steward waiver per the RFC 0021–0029 precedent. Remaining acceptance criteria (conformance scenarios, SECURITY invariant, INTEROP-MATRIX rows, reference-host emission) define the path to `Accepted`.

- **`spec/v1/ai-envelope.md`** — extended with §"Reasoning field (normative)" between §"Universal kinds (normative)" and §"Vendor-namespaced kinds". Normative SHALL: every envelope payload schema defined by this spec SHALL support an OPTIONAL `reasoning` field of type `string`. ### RFC 0024 (Draft) — Streaming `agent.reasoned` deltas (2026-05-18)

### `apps/workflow-engine@P3` — production-rollout fixes (post-mortem) (2026-05-18)

Twelve issues caught while bringing P3 up on the live `app.openwop.dev` deploy. None changed the wire contract or the test counts; every one is documented inline in `apps/workflow-engine/DEPLOY.md §"Phase 3 production-rollout gotchas (post-mortem)"` so the next bootstrap doesn't repeat the debug cycle.

- **Cookie name → `__session`** (commit `cacf2d7`). Firebase Hosting strips every cookie except `__session` when forwarding to Cloud Run. The original `openwop.session` was silently dropped on every API request, so the SPA minted a fresh anon tenant per request and the new `GET /v1/runs` always returned `{runs:[]}`. Renamed; configurable via `OPENWOP_SESSION_COOKIE_NAME` for non-Hosting deploys.
- **`ajv` declared as a prod dep** (commit `cacf2d7`). `src/host/mcpServerRouter.ts` imports it but it was only present as a transitive of a dev-only package. The Cloud Run runtime stage's `npm install --omit=dev` dropped it → container failed to listen on PORT=8080.
- **DemoHostBanner Rules-of-Hooks bug** (commit `a582e25`). `if (user) return null;` lived BEFORE a `useEffect`. When users signed in for the first time, the hook count dropped 4→3 and the whole SPA crashed on the sign-in commit with React error #300. Early return moved BELOW all hooks.
- **Modal portal** (commit `fd2090f`). Sign-in + delete-account modals rendered BEHIND `<main>` even with `z-index: 1000` because the `<header>` (their JSX parent) had `position: sticky` + `backdrop-filter`, both of which create stacking contexts. Switched to `createPortal(modal, document.body)` for both.
- **Modal centering** (commit `e74488d`). `align-items: center` clipped the title above the viewport on narrow windows. Switched to `align-items: start` + `padding-top: 8vh` + `overflow-y: auto`.
- **Link contrast** (commit `a582e25`). Bare `<a>` tags inherited the browser-default dark blue against the `--color-bg: #0b0e14` dark surface, unreadable. Added a global anchor style using `--color-accent`.
- **Cross-provider account linking** (commit `8335578`). When a Google-registered user tries to sign in with GitHub (or vice versa), Firebase rejects with `auth/account-exists-with-different-credential`. New `ExistingProviderSignInError` captures the pending credential + existing provider list. After the user signs in with the existing provider, `linkWithCredential` attaches the rejected credential to the same Firebase user — subsequent visits work with either provider.
- **Redirect-based sign-in** (commit `0bf42c3`). Replaced `signInWithPopup` with `signInWithRedirect` to eliminate the persistent `Cross-Origin-Opener-Policy would block window.closed` console warnings that Firebase's popup poller triggers. State persisted across page loads via sessionStorage; `processRedirectResult()` runs once at boot and dispatches success / link-required / error.
- **`Cache-Control: no-cache` on `index.html`** (commit `b2a91c1`). Firebase Hosting was caching `index.html` for 1 hour because a `**` catch-all COOP rule was overriding the per-index.html rule (Hosting applies only the LAST-matching source). Collapsed into a single rule that matches non-asset paths and carries both headers.
- **`authDomain` → custom domain** (commit `e785890`). `signInWithRedirect` returned a User but `getRedirectResult` returned null because the OAuth round-trip persisted state into the default-domain origin's storage; Safari ITP / Brave / Firefox TCP partition the third-party iframe's view of that storage on the SPA. Pointed `VITE_FIREBASE_AUTH_DOMAIN` at `app.openwop.dev` (Firebase Hosting auto-proxies `/__/auth/*` on custom domains). Same-origin throughout → `getRedirectResult` returns the user as expected.
- **OAuth client redirect URI ops note** (commit `e785890`). Firebase auto-syncs the default-domain redirect URI for Firebase-managed Google OAuth clients but NOT for custom domains. Manual step required in `console.cloud.google.com/apis/credentials`. Same applies to GitHub OAuth apps (independent of Firebase). DEPLOY.md §13 now spells it out.
- **Local dev → prod proxy** (commit `cb77d5a`). `vite.config.ts` defaults `/api/**` to forward to `https://app.openwop.dev`, so `npm run dev` in the frontend dir works against the live backend without spinning up a local Postgres / KMS / Firebase Auth. `cookieDomainRewrite: ''` strips the cookie's Domain attribute so the `__session` cookie binds to localhost. Override via `OPENWOP_DEV_PROXY_TARGET=http://localhost:8080`.

### `core.openwop.data@1.2.1` + `core.openwop.crypto@1.0.2` — correctness fix for nodes mis-declared as `pure` (2026-05-17)

Post-publish audit (see CHANGELOG `[Unreleased]` §"core.openwop.http@1.1.2" for the headline finding that motivated this sweep) surfaced 6 more nodes in the same defect class: declared `role: "pure"` + `capabilities: ["cacheable"]` while their runtime depends on wall-clock time or randomness. Under the engine's caching contract (`node-pack-manifest.schema.json` §"capabilities" — "engine uses these to decide caching"), a `pure + cacheable` node MAY be cached by input-hash, which for empty-input nodes like `uuid` collapses to "one cached value forever" and for time-dependent nodes returns stale data past expiration.

Patched (role: `pure` → `side-effect`, capabilities: `["cacheable"]` → `["side-effectful"]` — matches the canonical `core.openwop.http.fetch` declaration):

- **`core.openwop.data@1.2.1`** — `data.uuid` (uses `randomUUID()` — same defect class as the `http.idempotency-key@1.1.0` bug; empty inputs → input-hash collision → same UUID forever under `pure+cacheable`) + `data.datetime-now` (uses `new Date()` — workflows expecting fresh wall-clock time would get a frozen value).
- **`core.openwop.crypto@1.0.2`** — `crypto.jwt-mint` (uses `Date.now()` for `iat` claim; cached mints never refresh `iat`/`exp`), `crypto.jwt-verify` (uses `Date.now()` for `exp` check; **security**: cached "valid" past token expiration), `crypto.totp-generate` (uses 30-sec window; **security**: defeats TOTP rotation per RFC 6238), `crypto.totp-verify` (uses 30-sec window; **security**: cached "valid" past window).
- **No runtime behavior changes** — `index.mjs` files unchanged. The fix is purely the manifest's contract declaration: the engine now correctly caches outputs by `(runId, nodeId)` (replay-safe) and never by input-hash (no stale values across fresh executions).
- **Compatibility:** safety-fix per `COMPATIBILITY.md §3`. The pre-fix declarations were incorrect — these nodes never satisfied the `pure` contract. Workflow authors who hit the input-hash cache path in 1.2.0 / 1.0.1 were getting *worse* behavior than the spec promised.
- **Yank policy** consistent with the SSRF + JWT alg-confusion + idempotency-key batch: old versions remain immutable + accessible; deprecation flag flip lands ~2026-05-24 after the 7-day soak.
- **Publication:** built + signed + republished alongside this commit (same flow as `http@1.1.2`). `verify-signatures.mjs` confirms both new versions against `keyId=openwop-team-1`.

### `core.openwop.http@1.1.2` — idempotency-key generator made deterministic (2026-05-17)

Closes a correctness/security bug in `core.openwop.http.idempotency-key`: the previous default mode (`uuid`) returned a fresh `randomUUID()` on every call, defeating the entire point of an Idempotency-Key. Workflow authors composing `idempotency-key → fetch` were getting a different key on every retry, so the remote service treated each attempt as a new request — exactly what idempotency keys are supposed to prevent. Caught during the post-publication review of the 17 `core.openwop.*` packs published 2026-05-17.

- **`packs/core.openwop.http/index.mjs`** — `idempotencyKey()` rewritten. The `uuid` mode is **removed**; calls with `mode: uuid` reject with `CONFIG_INVALID` and an error message naming the safety-fix.
- **`composite` now reads `runId`/`nodeId` from `ctx`** (with `inputs.runId` / `inputs.nodeId` as overrides). Previously required them as inputs, which was awkward — the host already knows them. Both reference hosts (Postgres + SQLite) surface them on ctx.

### Pack patches: SSRF + JWT alg-confusion fixes (P0.1) (2026-05-17)

Closes 2 of the 3 High-severity findings from yesterday's pre-audit triage. First step of the `app.openwop.dev` public-deploy hardening (Phase 0). Three packs patched + republished to `packs.openwop.dev`; old versions remain available for pinned consumers.

- **`core.openwop.crypto@1.0.1`** — closes `OPENWOP-AUDIT-2026-001` (JWT alg-confusion / CVE-2015-9235 pattern). New required config fields `expectedAlgorithm` (single) or `allowedAlgorithms` (allow-list) bind the verifier to specific algorithm(s); the token's self-declared `alg` is checked against the caller's allow-list BEFORE any key material is touched. Calls without either field reject with `JWT_VERIFIER_ALGORITHM_REQUIRED` (override for legacy callers: `OPENWOP_JWT_ALLOW_HEADER_ALG=true`, deprecated). JWKS verification gains a `kty`-vs-`alg` cross-check so an `HS256` token can't be verified against an `RSA` JWK by treating the public key bytes as an HMAC secret. Schema: `jwt-verify.config.json` `$id` bumps to `/1.0.1/`.
- **`core.openwop.http@1.1.1`** — closes the http half of `OPENWOP-AUDIT-2026-002` (SSRF). All outbound `fetch()` calls now route through a `safeFetch()` wrapper that: (a) rejects non-http(s) schemes; (b) DNS-resolves the destination hostname and rejects any address in loopback/`127.0.0.0/8`, link-local/`169.254.0.0/16` (covers GCP/AWS metadata), RFC 1918 (`10/8`, `172.16/12`, `192.168/16`), CGNAT (`100.64/10`), multicast (`224/4`), and the IPv6 equivalents (`::1`, `fe80::/10`, `fc00::/7`, `ff00::/8`, with `::ffff:` IPv4-mapped re-checked); (c) strips `authorization`, `cookie`, `proxy-authorization`, `set-cookie` from caller-supplied `inputs.headers`. The retry loop now refuses to retry SSRF-block / scheme-block / DNS-fail errors (they're deterministic). Opt-out for local-dev / self-hosted: `OPENWOP_HTTP_ALLOW_PRIVATE_RANGES=true` on the host process. Production `app.openwop.dev` runs with it unset.
- **`core.openwop.rag@1.0.1`** — closes the rag half of `OPENWOP-AUDIT-2026-002`. `loader-url` and `loader-github` now share an inlined `safeFetch()` (same block-list as the http pack) so they can't be used as SSRF pivots even on hosts that don't restrict pack-level fetch. Also strips `authorization` / `cookie` from caller-supplied `inputs.headers` so a workflow piping LLM output into `headers` can't exfiltrate a verifier bearer.
- **Yank policy.** Old versions (`crypto@1.0.0`, `http@1.0.0`/`1.1.0`, `rag@1.0.0`) stay accessible but will be flagged `deprecated` in the registry index in a follow-up commit (avoid breaking pinned consumers immediately). Yank decision happens after the new versions have soaked on the registry for 7 days. Severity-`high` advisory IDs will be assigned when the external audit confirms gradings.
- **Verification.** All three patched packs verify against `keyId=openwop-team-1` via `registry/scripts/verify-signatures.mjs` (69 / 69 verified). Smoke tests live-confirmed:
  - SSRF: `http://169.254.169.254/`, `http://localhost/`, `http://10.0.0.1/`, `http://[::1]/`, `file:///etc/passwd` all blocked; `https://example.com/` returns 200.
  - Header scrub: caller-supplied `Authorization` + `Cookie` headers stripped before fetch dispatches; an `X-Marker` non-sensitive header passes through.
