# OpenWOP Spec v1 — Changelog

All notable changes to the openwop v1 spec, schemas, OpenAPI/AsyncAPI, conformance suite, and reference SDKs.

Format follows [Keep a Changelog](https://keepachangelog.com/en/1/) loosely. Versions are spec-corpus-wide (one date, multiple artifact updates per row); per-artifact versions live in their respective `package.json` / schema `$id` fields.

> **Status legend** (per [`/governance/spec-status/`](https://openwop.dev/governance/spec-status/)):
> Stable · Stabilizing · Draft · Experimental — see individual doc headers for current state. The legacy `STUB / DRAFT / OUTLINE / FINAL` vocabulary still appears in older releases below; both are valid in the corpus.

> **Package version map.** The version headers below are **spec-corpus** versions, not package versions — each package advances independently on its own per-package release tag. A deep-link like `#v1-1-6` therefore has no anchor here by design — the TS SDK's own history lives in [`sdk/typescript/CHANGELOG.md`](https://github.com/openwop/openwop/blob/main/sdk/typescript/CHANGELOG.md) and on npm. ## [Unreleased]

- **Correction — RFC 0138 offered a migration strategy that would break replay; the `artifactTypeId` constraint is protocol-wide, not host-local (2026-08-07).** Prose-only; no wire shape, schema, or normative clause changes, and the RFC's actual proposal (the extension hatch) is untouched and unaffected. RFC 0138 §"Implementation notes" originally answered the reference host's `artifactTypeId` namespace-migration blocker by offering three legitimate strategies, the first being *"migrate durable rows behind a backfill."* **That was wrong for every conformant host.** `artifact-type-packs.md` §"Manifest fields" states that `artifactTypeId` **is the value** `WorkflowNode.artifactType`, `nodes[].artifact.typeId`, and **`artifact.created.artifactType`** reference, and `run-event-payloads.schema.json` `$defs/artifactCreated` carries `artifactType` as a payload field — so the value is written into the **run-event log**, which `replay.md` §"Determinism guarantees" treats as fixed history. A host that rewrites historical `artifact.created.artifactType` values to migrate a namespace is rewriting the event log, and `POST /v1/runs/{runId}:fork` against a pre-migration checkpoint no longer replays what happened. **The corrected position:** a read-side alias map (canonical → native, resolved on lookup, never rewriting a stored or emitted id) is the available strategy, and because historical events are immutable it is **permanent, not transitional** — a host planning to delete it later has misunderstood the constraint. Rewriting historical values is not available. **The failure mode that makes the alias dangerous to half-implement:** aliasing the lookup helpers but not the validation path yields a canonical id that reports `registered: true` and then falls into the unregistered escape hatch — an artifact **silently untyped on a green run**, worse than the non-conformant name it replaced, which at least failed visibly. **Why the original was wrong, since the reasoning generalizes:** the RFC reasoned about `artifactTypeId` from its *storage* — the reporting host described it as living in "a persisted field" and the RFC accepted that framing and answered a database question. The right question was where the value travels on the wire; one grep of `run-event-payloads.schema.json` would have made the replay constraint immediate. That is the same defect this RFC's own conformance section documents in another guise: reasoning about a component instead of the path a value takes. **Credit:** surfaced by the openwop-app reference host, which independently reached the no-backfill conclusion for itself while migrating both shipped artifact-type packs against the 0138 hatch; the steward's contribution was establishing that it binds every host, not only theirs. Gap **G5** escalated accordingly (the corpus still lacks prose stating that legacy ids were never wire-conformant *and* the replay constraint, currently derivable only by composing three documents — RFC 0071's owners' RFC to file). New gap **G8** records that the fact the correction rests on is exercised only by `artifact-type-pack-install.test.ts`, one of the three G14 bare-`return` soft-skip scenarios, so it reports green against a host that never emits the event — nothing pins it always-on. The erroneous text is superseded in place with a dated correction notice rather than silently rewritten; git history retains it.

- **RFC 0138 — pack manifests now admit a vendor-extension hatch; the corpus mandated a behavior for a case it structurally forbade (2026-08-06).** Additive per `COMPATIBILITY.md` §2.1; no existing property touched and every manifest valid before this change remains valid byte-for-byte. `host-extensions.md` §"Vendor-prefixed namespaces" carries a normative MUST — *"a client receiving an unknown vendor-prefixed field MUST treat it as opaque"* — but **every** pack manifest set `additionalProperties: false` with no pattern escape, so such a field could not legally exist on one. A survey found **not one** of the eight manifests carried any `patternProperties` anywhere: the closed posture was uniform, and so was the contradiction. A tier-1 reference host was blocked migrating `community.openwop.canvas-checklist`, whose load-bearing `x-openwop-app.canvas` key registers a canvas component catalog — its only conformant options were to drop a working feature or stop publishing the pack. **Fix:** an `^(x-|vendor\.)` hatch at the root and per-item entry object of all eight pack manifests **and the registry publication contract** — 16 hatch sites. Including `registry-version-manifest.schema.json` is not incidental: its per-item arrays were already loose (RFC 0107 G1) but its **root** was closed, so a root-level extension validated against its source manifest and was then **rejected at registry `PUT`** — the same split-brain one layer down, measured with a probe rather than assumed. **The hatch is narrow:** a misspelled canonical field (`dispalyName`) is still rejected, because typo detection is what `additionalProperties: false` is actually for. **The prose is the substance, not the schema.** "Ignore" is defined normatively rather than left advisory — a consumer that does not recognize an extension MUST NOT render it, execute it, interpret it as markup or a templating directive, use it to select a code path, or persist it into a surface where it will later be interpreted; retaining raw bytes for round-trip fidelity is fine, acting on them is not. An extension value is **pack-authored, therefore untrusted**, on the `form-content-pack-string-trust-boundary` precedent: a signature proves authorship, not content safety. A hatch that hosts half-honor by stashing untrusted blobs into rendering paths is **strictly worse than no hatch**, converting a loud publication failure into a silent injection surface. Extensions are also **not** a capability-negotiation channel, and deliberately **no** capability flag is defined — one would let a host advertise its way out of a MUST. New `pack-manifest-extension-opaque` protocol-tier invariant + threat-model row, landing with the MUST-NOT they enforce. **Honest limits:** enforcement is corpus-side only — no leg exercises a *host* accepting an extended manifest or honoring MUST-ignore, since that needs a host-sample seam behind `behaviorGate` (gaps G6/G7; the same class of hole that let a reference host's loader accept only inline `schema` while silently rejecting `schemaRef`). The related persisted-`artifactTypeId` migration constraint is **answered, not solved** — a host-side data concern this protocol declines to require surface for; the prose stating that legacy ids were never wire-conformant belongs to RFC 0071's owners (G5). **A near-miss worth recording:** the first draft of the conformance scenario enumerated manifests by naming convention and silently skipped `frontend-plugin-manifest.schema.json` because its name lacks `-pack-`; the leg now asserts an explicit in-scope count of 9, so a new pack kind fails until its author either wires the hatch or names the exclusion. Non-vacuity sabotage-verified: widening a pattern to `^.*` reds 3 legs, removing a hatch reds 1. Suite `1.62.0 → 1.63.0` (new scenario file ⇒ minor).

- **`Conformance Soak` un-wedged — the chain-expansion drift gate was comparing the wrong thing (2026-08-05).** Gate-scoping only; no wire-shape, schema, or normative change, and the expansion algorithm itself is untouched. The scheduled `Conformance Soak` workflow had failed **40 consecutive runs on `main`, back to at least 2026-07-11** — roughly a month permanently red. It never surfaced on a pull request because the soak runs **post-merge only**, the same blind spot that stranded the 155→156 registry count. **Root cause:** `scripts/check-workflow-chain-expansion-sync.mjs` asserts byte-equality between the spec-authoritative `conformance/src/lib/workflow-chain-expansion.ts` and the in-memory reference host's zero-deps mirror, but the conformance side had no end marker, so the compared region ran to EOF: **33 KB against 4.5 KB, 32 declarations against 6**. The gate was demanding the host mirror three later feature waves — RFC 0124 deferred parameters and RFC 0133 sub-chain co-expansion + produced variables — that are **capability-gated** and that a minimal host is not obliged to implement. RFC 0133 in fact requires a host that does not advertise `workflowChainPacks.subChains` to **REFUSE** that surface with `sub_chain_unsupported`, never to carry it; the in-memory host advertises neither `workflowChainPacks` nor `subChains`, so a byte-mirror demand was incoherent, not merely noisy. **Fix:** an explicit `// ─── End of the MIRRORED CORE` sentinel in the authoritative file closes the base algorithm every chain-loading host shares, and the script now ends the compared region at whichever sentinel a file carries. The sentinel documents which surfaces are excluded and why, and says plainly that it must not be moved to silence a failure — base-algorithm changes go above it and the mirror follows; capability-gated surfaces go below. **Honest status:** this does NOT turn the soak green on its own, and is not claimed to. Scoping removes 25 spurious surfaces and leaves the genuinely-shared core, where two real deltas remain, both owned by `openwop-examples`: (1) the WCP2 whole-value typed-resolution port, already in flight on that repo's pushed `sync-wcp2-whole-value-typed` branch — deliberately not duplicated here; and (2) **a one-line functional gap, `triggerRule` pass-through in `rewriteEdgeRef`** — without it the RFC 0125 fan-in/error-routing rule is **silently dropped at expansion**. Verified by running the scoped gate against that branch's file content: with WCP2 applied the residual is exactly that one line.

- **Capability discovery keys — the PLAIN family name is canonical; three conformance helpers corrected (RFC 0137 G16, 2026-08-05).** Conformance-only; no wire-shape, schema, or normative change. `readArtifactTypesCap`, `readCardPacksCap` and `readFormContentCap` read a **dotted** `host.artifactTypes` / `host.chat` / `host.forms`, which made a schema-following host **invisible** to those scenarios — they soft-skipped to green while the host implemented the behavior. **The measurement that settles it** (supplied by the reference host, verified by the steward): `schemas/capabilities.schema.json` declares **82 properties and ZERO dotted `host.*` keys**, and — decisively — **five host capabilities are already declared PLAINLY**: `fs`, `kvStorage`, `tableStorage`, `queueBus`, `scheduling`, each mapping to a `§host.<name>` section in `host-capabilities.md` (`§host.fs` ↔ `fs`, `§host.kvStorage` ↔ `kvStorage`, …). The corpus already had a pattern and the three helpers contradicted it. The `host.` prefix is the capability **identifier** notation — prose `§` headings, pack `peerDependencies`, `error.capability` — **not** the discovery-document key. Helpers now read **plain-root → dotted-root → plain-wrapper → dotted-wrapper** (root before wrapper per `capabilities.md` §"Document-root layout (normative — RFC 0073)"; the wrapper arms retire with the migration window at v2.0). Verified against a stub host in all four spellings, with an unadvertised host still failing loudly under `OPENWOP_REQUIRE_BEHAVIOR=true`. **Why this is not the fork this RFC refused for field types:** that was a *pack-authored wire vocabulary* where a second spelling would have forced every host to guess. This is a *read-side tolerance* for an ambiguity that already existed between two corpus artifacts, and the alternative was leaving conformant hosts silently untested. **Consequence to expect:** the RFC 0071 artifact-type and chat-card behavioral legs will now actually RUN against hosts that were previously invisible — they may fail where they previously skipped, which is the point. Declaring the `host.*` families explicitly in `capabilities.schema.json` remains worthwhile and is left to the RFCs that own them. **G16 closed; G14 unblocked** (the remaining `behaviorGate` flip makes those legs enforced rather than merely visible). - **RFC 0137 clarification — `degrade` vs `refuse`, and the routing ban binds the pack, not the host (2026-08-05).** Editorial: no wire-shape, schema, or normative change — both rules were already implied; the reference host read one of them the other way while implementing, so the text now says it outright. **(1) §Instantiation #2** gains a three-row table separating the cases a host MUST treat differently: a portable-subset member maps to its data kind; a **well-formed but unrecognized `vendor.<org>.<kind>` / `x-<kind>` extension MUST degrade** to a plain text input (refusing it breaks forward compatibility — the extension is valid and simply belongs to another host); **anything else MUST be refused**, because the `type` pattern admits only the subset and the two prefixes, so a bare unknown (`emial`, `textarea`, `email`) means the pack is *malformed*, not extended. Degrading a malformed value would discard what the author declared — a mistyped `select` losing its closed option set to a free-text box is a real hazard on a public form. A host MUST NOT collapse the two into one rule in either direction. The host had implemented refuse-everything (defensible on its own terms, and non-conformant on the extension arm). **(2) §"No submission routing"** gains an explicit scope sentence: the ban constrains the **pack**, not the host. A host may route submissions wherever its **operator** configures — intake binding, CRM list, queue, workflow trigger; the requirement is that the destination is chosen by the operator and never declared by a pack author or derived from pack-authored content. A form instantiated from a template begins with whatever routing a hand-authored form would get (typically none), configured afterward as usual. Suite `1.60.0 → 1.60.1` (31 tests, +2 legs asserting both clarifications).

- **RFC 0137 amendment — implementer feedback from the reference host, same day, still `Active` (2026-08-05).** The load-bearing wire decisions are **unchanged** (shared RFC 0071 field-type subset, `format`-not-type, `id`-not-`key`, SemVer `templates[].version`); this amendment adds two normative sections and corrects four bounds. **(1) §"Unique identifiers"** — duplicate `templates[].templateId` / `fields[].id` MUST be refused at registry `PUT` / install. Framed as **data integrity**: two fields sharing an `id` silently overwrite one another in the submission value bag, so a user's answer is lost with no error. Enforced as prose + a registry/host check because JSON Schema 2020-12 cannot express uniqueness-by-property (`uniqueItems` compares whole objects) — the same treatment `nodes[].typeId` / `artifactTypes[].artifactTypeId` / `cards[].cardTypeId` already get. **(2) §"No submission routing" (F2)** + new protocol-tier invariant **`form-content-template-no-submission-routing`** — a template describes a form's SHAPE and MUST NOT describe where its submissions go; `FormTemplate` declares no destination/binding/webhook/list-id property and rejects one via `additionalProperties: false`, and a host MUST NOT infer a destination from another field. Not redundant with `additionalProperties: false`: the invariant binds **future** evolution — should a routing surface ever be added, routing MUST remain a host-side decision made by the operator behind explicit consent, never bound unilaterally by a pack. Where a tenant's submissions land is a decision about the OPERATOR's data, frequently personal data with legal obligations; a signed manifest confers authorship, not authority. Structurally identical to `org-position-no-authority-escalation` (RFC 0087). **(3) Bounds RELAXED on adopter evidence** — field `label` 200 → 1000 (a lawful GDPR/marketing consent label routinely exceeds 200 chars) and `options` 200 → 250 entries (a country list is ~195 against a 200 cap); both accept strictly more, so nothing previously valid becomes invalid. **(4) Outer resource caps ADDED** — `templates[]` ≤ 100, `fields[]` ≤ 200. Honestly classified: a narrowing is **not** `additive` in the general case. It is safe here on specific grounds — RFC 0137 landed hours earlier and **zero form-content packs exist in any registry**, so the invalidated set is empty — and the caps sit well above the host's own tighter product policy (50 fields / 20 templates), because the wire's job is an outer render-bomb bound and a wire cap tighter than legitimate use is itself an interop hazard. **(5) §"Host storage is out of scope"** — the single-vocabulary rule binds the WIRE; a host MAY keep an internal field representation and translate at the pack boundary (an anti-corruption layer), which is one wire vocabulary plus a private implementation detail, not a fork. Migrating stored rows instead can silently collapse a multi-line field and hard-fail host logic keyed on internal type names. Also confirmed: a bare `templateId` like `forms.contact-us` is **invalid** — the reserved-scope pattern (`core|vendor|community|private`) is unchanged, since exempting one kind would open a namespace-squatting hole. Suite `1.59.0 → 1.60.0` (29 tests, +6 legs). Totals: 158 invariants (128 protocol / 28 reference-impl / 2 advisory). New cross-kind gap **G11**: identifier uniqueness is prose-only for *every* pack kind and `registry-operations.md` names no duplicate-id check for any of them — a corpus-wide follow-up, not fixed unilaterally here.

- **Form-content packs — a sixth declarative pack kind (RFC 0137 `Draft → Active`, 2026-08-05).** Adds `form-content` to the publishable pack kinds (RFC 0107): a pack carrying **`templates[]`**, where a template is a named, SemVer-versioned, ordered set of typed input fields a host instantiates into an ordinary, **fully editable** form through its **normal create path**. The kind is inert by construction — no `runtime`, no entry point, no handler, and it MUST NOT cause a host to accept a form, field, or submission surface it would not otherwise accept; submitted values are sanitized/validated/authorized exactly as hand-typed input. New `schemas/form-content-pack-manifest.schema.json` (authoritative source contract) + `spec/v1/form-content-packs.md` + `host-capabilities.md` §host.forms (`host.forms.contentPacks`). **The field-type vocabulary is deliberately NOT new:** `fields[].type` reuses the closed portable subset already settled for chat-card packs (`chat-card-packs.md` §"Input fields", RFC 0071 gap G9 resolved 2026-05-27) — `text`/`longtext`/`number`/`boolean`/`select`/`multiselect`/`file`/`artifact-ref` plus the `vendor.<org>.<kind>` / `x-<kind>` escape hatch and its "unrecognized ⇒ degrade to a plain text input" contract. Two declarative kinds that both collect typed user input MUST agree on what a field type means; a conformance leg asserts the two `type` patterns are **byte-identical** so neither can be widened alone. Validation formats ride a separate optional `format` (`email`, `uri`, `date`, `date-time`, `time`, `x-*`) rather than joining the `type` enum — `email` is a constraint on text, not a data kind, and admitting it would let the subset accrete back into a widget catalog.
