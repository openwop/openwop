# Key rotation

Two key surfaces are rotated two different ways, for one structural reason: **a pack can be re-signed and a certification bundle cannot.** Read the split first; the procedures are not interchangeable.

## The split

| | Host bundle signing | Pack publishing |
|---|---|---|
| Where the key is published | the host's own `/.well-known/openwop`, `signingKeys[]` | the registry's `.well-known/openwop-registry.json`, `signingKeys[]` |
| Encoding | raw 32-byte Ed25519 public key, base64url unpadded — **exactly 43 characters** | SPKI PEM |
| Trust root | **self-asserted.** A verifier resolves `keyId` in the host's own document; no list the steward keeps | steward-mediated, with `permittedNamespaces` |
| Old key after rotation | **MUST stay listed, forever** | MUST stay listed while any served version names it (yanked versions stay served) |
| Governing text | [`spec/v2/core/conformance.md`](../../spec/v2/core/conformance.md) §"Bundle v3" | [`spec/v2/core/packs.md`](../../spec/v2/core/packs.md) §"Signing", [RFC 0222](../../RFCS/0222-v2-registry-operations.md) §C |

The asymmetry is not an inconsistency. A pack can be published again, as a new version, under a new key. **A certification bundle is immutable evidence** — it was signed once, over a witness digest, and re-signing it would mean re-cutting it against a host that has since changed.

## Host bundle-signing rotation

`spec/v2/core/conformance.md` §"Bundle v3" is normative:

> A retired key MUST stay listed.

Removing it silently invalidates every bundle it already signed.

Procedure:

1. **Generate the new pair.** Ed25519, PKCS8 private key. `docs/IMPLEMENT-CORE.md` §"Signing keys" carries the two-command recipe, including the derivation of the 43-character public form — do not reuse an `openssl genpkey` recipe written for pack signing, which emits SPKI and will not match the pattern.
2. **Publish the new key alongside the old one.** Both entries live in `signingKeys[]` at once. Nothing is removed at this step.
3. **Cut the next bundle under the new key id** (`--signing-key-id <new>`). Bundles already cut keep naming the old id, and keep verifying, because the old key is still published.
4. **Stamp `retiredAt` on the old entry.** Never delete it.

### What `retiredAt` is, and is not

`retiredAt` is **advisory**. No verifier in the corpus reads it: `check-cut-gates.mjs` resolves `signature.keyId` against `signingKeys[]` by id alone, and `verifyBundleV3` takes a caller-supplied key. **A key retired years ago verifies exactly like a live one.**

It cannot be made enforceable at this layer, and it is worth knowing why rather than filing a bug. The signature covers exactly four members — `witnessSha256`, `host.build`, `suite.version`, `discovery.sha256` — and `generatedAt` is **outside** it. So "was this bundle signed before the key was retired" is not decidable from the bundle: the one timestamp that would answer it is unsigned and editable. Making it decidable means changing `SIGNATURE_OVER`, which is a schema `const` and would invalidate every bundle's `over` value. That is an RFC, not a runbook edit.

One real lever does exist. Because `discovery.sha256` **is** signed, a bundle that embeds `discovery.document` freezes the key list under its own signature — so a bundle cut *after* a key was stamped `retiredAt` carries that stamp inside its own signed evidence, and one cut before does not. That works only if `retiredAt` is set at rotation time rather than backdated later.

Set it anyway. It is a promise to a reader, and the reader has no other signal.

## Pack-publishing rotation

See [`PACK-LIFECYCLE.md`](./PACK-LIFECYCLE.md) §"Key rotation". Add the new key with `status: "active"` and change the old key's `status` to any other value (the registry uses `rotated`). Only an `active` key may sign a new publication.

The old key stays listed. `packs.md` requires a key to stay listed while any served version names it, and a verifier MUST NOT refuse a version because its key is not `active`. A yanked version is still served, so yanking does not release its key either. In practice a pack-signing key is retired, not removed — the same outcome as for bundles, reached by a different rule.

Compromise is a different procedure: [`INCIDENT-RESPONSE.md`](./INCIDENT-RESPONSE.md) incident class 3.

## Known gap

No conformance scenario exercises rotation, overlap, or retirement on either surface. The host half would go in `conformance/src/coherence/v2-bundle-signature-attributable.test.ts`, which today asserts the *shape* of `signingKeys[]` without ever resolving a rotated id.

## Maintenance hazard

The bundle canonicalizer and the attestation preimage exist in **two independent copies** — `conformance/src/lib/certification-bundle-v3.ts` and `scripts/check-cut-gates.mjs` — and must stay in lockstep or a bundle will verify in one place and not the other. Both bundle schemas are generated by `scripts/generate-from-declaration.mjs`: edit the generator, never the schema.
