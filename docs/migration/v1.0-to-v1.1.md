# Migrating from OpenWOP v1.0 to v1.1

> **TL;DR — no code changes required.** v1.1 is **purely additive** per [`COMPATIBILITY.md`](../../COMPATIBILITY.md) §2.1. Every v1.0 conformance pass remains valid in v1.1. v1.0 clients call v1.1 hosts unchanged; v1.0 hosts continue to serve v1.0 clients unchanged. This guide enumerates what's _new_ so adopters can decide what to opt into.

## Why this doc exists

v1.0 published 2026-05-11 (npm + PyPI + Go modules). v1.1 published 2026-05-13 as the close-out release for v1.0 with 18 additive capability surfaces. Because v1.0.0 cannot be re-published (the registries treat each version as immutable), v1.1.0 is the version users `npm install` / `pip install` / `go get` to get the close-out work — but the **protocol contract is unchanged**.

This guide is for adopters who:

- Wrote a host against v1.0 and want to know which optional surfaces they could now advertise.
- Wrote a client against v1.0 and want to know which capability blocks they could now consume.
- Pinned to `@openwop/openwop@1.0.0` and want to understand what they get by bumping to `^1.1.0`.

## Wire-shape guarantee

| Surface                                    | v1.0 → v1.1                                                             | Adopter action                                                                                        |
| ------------------------------------------ | ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| REST + SSE endpoint contracts              | Unchanged                                                               | None                                                                                                  |
| Required schema fields                     | Unchanged                                                               | None                                                                                                  |
| Existing event-type shapes                 | Unchanged                                                               | None                                                                                                  |
| Existing `MUST` requirements               | Unchanged (none relaxed)                                                | None                                                                                                  |
| Error-code meanings + HTTP status mappings | Unchanged                                                               | None                                                                                                  |
| `/.well-known/openwop` discovery shape     | Additive only — new optional capability blocks; existing keys identical | Clients MUST tolerate unknown capability blocks per [`COMPATIBILITY.md`](../../COMPATIBILITY.md) §2.1 |

If your v1.0 implementation passes `@openwop/openwop-conformance@1.0.0`, it passes `@openwop/openwop-conformance@1.1.0` without modification.

## What's new (additive)

### Phase H — BYOK + provider integration (myndhyve.ai launch-blockers)

Each capability is opt-in. Hosts advertise via `/.well-known/openwop`; absence is a valid v1.1 state.

| Capability                 | RFC / Spec                                                                         | Adopter implication                                                                                                                                                                                                                          |
| -------------------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `capabilities.secrets`     | [`auth.md`](../../spec/v1/auth.md) §"Secret resolution"                            | Hosts MAY advertise BYOK secret resolution (host-managed, tenant scope). Clients consuming `credentialRef` references gain provider-agnostic auth.                                                                                           |
| `capabilities.aiProviders` | [`host-capabilities.md`](../../spec/v1/host-capabilities.md) §`host.aiProviders`   | Hosts MAY advertise AI-provider routing with 4-mode policy enforcement (`disabled` / `optional` / `required` / `restricted`) for `core.llm.chat` + `core.llm.completion` + `core.llm.imageGeneration`.                                       |
| `capabilities.mcpClient`   | [`mcp-integration.md`](../../spec/v1/mcp-integration.md)                           | Hosts MAY advertise MCP tool invocation via `core.mcp.toolCall` over HTTP/JSON-RPC. `trustBoundary: "untrusted"` is normative per [`SECURITY/threat-model-prompt-injection.md`](../../SECURITY/threat-model-prompt-injection.md) §UNTRUSTED. |
| `capabilities.httpClient`  | [`host-capabilities.md`](../../spec/v1/host-capabilities.md) §`host.httpClient`    | Hosts MAY advertise `core.http.request` (6 methods, SSRF guard, 1 MiB response cap).                                                                                                                                                         |
| `capBreached` kinds        | [RFC 0008 §K](../../RFCS/0008-wasm-abi.md)                                         | Existing `cap.breached` event's `kind` enum gained `wasm-memory`, `wasm-fuel`, `wasm-execution-time` alongside the original four. Pre-1.1 hosts emit only the original four; consumers MUST tolerate the new kinds.                          |
| SDK helpers                | [`sdk/PARITY.md`](https://github.com/openwop/openwop-sdks/blob/main/sdk/PARITY.md) | TypeScript / Python / Go SDKs gained typed exports for `MemoryEntry`, `AgentRef`, `AICredentialRef`, `McpToolCallNodeConfig`, `HttpRequestNodeConfig` + 17 new error codes.                                                                  |

**Two new protocol-tier SECURITY invariants** land in [`SECURITY/invariants.yaml`](../../SECURITY/invariants.yaml): `mcp-toolcall-payload-redaction` + `http-client-ssrf-guard`. Both have public conformance tests; hosts not claiming the capabilities are unaffected.

### Phase G — spec-corpus close-out (editorial discipline)

All [`spec/v1/*.md`](../../spec/v1/) prose docs at `Status: FINAL v1`. New additions since the 2026-05-08 freeze that adopters might care about:

- [`auth-profiles.md`](../../spec/v1/auth-profiles.md) — the 5 named auth profiles consolidated; precise enum vocabulary for the `capabilities.auth.profiles[]` array.
- [`grpc-transport.md`](../../spec/v1/grpc-transport.md) — `api/grpc/openwop.proto` canonical `openwop.v1.Engine` gRPC service; profile-gated via `capabilities.supportedTransports: ["grpc"]`.
- [`production-profile.md`](../../spec/v1/production-profile.md) — the `openwop-production` profile predicate; first claimed by the Postgres reference host.
- [`replay.md`](../../spec/v1/replay.md) §"Retention and expiry" + §"LLM cache-key recipe" annexes.
- [`node-packs.md`](../../spec/v1/node-packs.md) §"WASM runtime" (RFC 0008 cross-link) + §"Lockfile" annex.

### Conformance probe improvements (no host action)

- **OTLP/gRPC collector** ships in `conformance/src/lib/otel-collector.ts` (hand-rolled `node:http2`-based, zero npm deps). Hosts emitting `OTEL_EXPORTER_OTLP_PROTOCOL=grpc` now have an in-suite target.
- **MCP probe** supports all three MCP transports (`application/json`, `text/event-stream`, stdio-bridged). The new `examples/mcp-stdio-bridge/` shim lets operators run any stdio MCP server against the openwop probe.

## Upgrading

```bash
# TypeScript
npm install @openwop/openwop@^1.1.0
npm install @openwop/openwop-conformance@^1.1.0

# Python
pip install --upgrade openwop-client

# Go
go get -u github.com/openwop/openwop/sdk/go@v1.1.0
```

No source-code changes required. If you want to consume any of the new capability blocks, gate on the corresponding discovery field at runtime — the openwop client SDKs surface them as typed fields on the discovery response.

## What's NOT in v1.1 (deferred to v1.2 or post-1.x)

Per the v1.2 outlook in [`ROADMAP.md`](../../ROADMAP.md):

- **RFC 0012 — memory compaction profile** — currently `Draft`; gates on host-side carry-forward implementation.
- **Component Model WASM packs** (`runtime.language: "wasm-component"`) — manifest enum reserved; capability flag declared; loader implementation gated on adopter demand.
- **Rust SDK** — demand-gated; the conformance suite is language-agnostic so future Rust clients test against the same wire contract.
- **4 audit-gated `core.openwop.{ai,http,mcp,triggers}` packs** — built + signed in-tree; publication to `packs.openwop.dev` gated on external audit completion per [`SECURITY/external-audit-engagement.md`](../../SECURITY/external-audit-engagement.md).
