# OpenWOP compatibility corrections log

> **Historical record.** These are the dated corrections and safety-fix classifications recorded under [`COMPATIBILITY.md`](../COMPATIBILITY.md) §3, moved here verbatim on 2026-09-27 so the policy page stays readable. A citation of "COMPATIBILITY.md §3" for a correction on record resolves to its entry below. New entries are appended here. `spec/v2/corrections.json` rows quote their entry from this file, and `scripts/check-v2-retirement.mjs` fails when the quote drifts.

**Editorial correction on record (2026-08-16, S22 — the error-envelope "schism"):** the HTTP error envelope is and was FLAT (`error` string + `message` + `details`, `error-envelope.schema.json`, `additionalProperties: false`); a nested `{ error: { code, retriable } }` shape that appeared in three `rest-endpoints.md` code-list entries, four test-seam contracts and ~15 scenarios between 2026-06 and 2026-08 was corrected back to flat with `details.retriable`. Not a safety-fix and not a wire change — no conforming host emitted the nested shape on a canonical endpoint; test seams that did get a tolerance window. Re-shaping `error` to an object would have been a §2.2 break, which is why the schema won.

**Conformance-affecting correction on record (2026-08-18, RFC 0057 §D — the replay re-emission note).** RFC 0057 §D carried a non-normative implementation note that read as permission for a `replay` fork to *suppress* recorded-fact events rather than re-emit them, and conceded in its own words that it satisfied only the "MUST NOT regenerate" half of the rule. `replay.md` §"Determinism guarantees" caveat 5 has required re-emission since v1.2 and did not change; the note is retired. **Recorded here because the change is conformance-affecting even though no requirement moved** — W3C Process **Class 3** ("corrections that MAY affect conformance, but add no new features", including one that "clears up an ambiguity ... in such a way that an agent whose conformance was once unclear becomes clearly conforming or non-conforming"), not Class 2 editorial. A suppressing host is now clearly non-conforming where its status was previously arguable; it was never conforming, but the corpus now says so unambiguously. Not a §2.2 break (no shape, code, or `MUST` changed) and not a §3 safety-fix (nothing that was conforming stops being so).

**Conformance-affecting correction on record (2026-08-25, `a2a-push-egress-ssrf` — the missing scheme arm).** RFC 0100 §4, `a2a-integration.md` §D.6, and the `a2a-push-egress-ssrf` invariant all required a caller-registered `pushConfig.url` to "pass the RFC 0093 webhook-egress SSRF guard", then abbreviated that guard — in every one of its statements — as "no private/loopback/link-local target". The guard it names is the `webhooks.md` §"SSRF protection" list, whose **first** entry is "Non-`https://` protocols". A reader could take the parenthetical as the definition rather than as shorthand for the referenced list, and a host refusing `http://10.0.0.5/push` on the address while accepting `http://push.example.com/` then read as conforming. **W3C Process Class 3**, on the same reasoning as the RFC 0057 §D entry above — a correction that "clears up an ambiguity … in such a way that an agent whose conformance was once unclear becomes clearly conforming or non-conforming". No `MUST` moved, no shape changed, and nothing that was conforming stops being so: a host accepting a plaintext push target was never conforming, because the guard it was told to apply always included that arm. Not a §2.2 break and **not** a §3 safety-fix. The conformance leg was also two-sided in the same change: the single `http://10.0.0.5` probe is refused by *either* arm alone, so it witnessed neither — an assertion that passes on half an implementation. **Reported by a tier-1 host** that found the identical structural defect in its own A2A path after fixing it on the webhook path, and **declined to fix it** on the grounds that the obligation reached A2A only by inference. That judgement was correct and is what made this a corpus defect rather than a host one.

**Conformance-affecting correction on record (2026-09-18, `trigger-event.deliveryId` — an equality no string could satisfy).** `schemas/v2/trigger-event.schema.json`'s `deliveryId` description asserted that the field *"equals the `causationId` stamped on `run.started`"*. That was true in v1, where both were free strings. RFC 0184/0187 made `deliveryId` tenant-bound — `^(anon:)?[…]{1,128}/[…]{16,128}$`, a `/` REQUIRED — while `causationId` stayed typed as `eventId`, whose character class admits no `/`. The two grammars have empty intersection, so **no implementation could satisfy the contract**, which is what makes this a Class 3 correction rather than a safety-fix: nothing that was conforming stops conforming, because conforming was impossible. Nothing relied on it — the v2 `deliveryId` kind has no read surface in `api/v2/openapi.yaml` at all, and no committed host bundle carries the pairing. The claim is removed; how a run points back at its causing delivery is left to the RFC that gives `deliveryId` a wire surface (RFC 0187 §Unresolved), where RFC 0040 §Alternatives' rejection of overloading `causationId` for a cross-space pointer already applies. **Corrected again 2026-09-18 (2.6.1): the first correction half-landed.** The same equality survived verbatim on `run-event-payloads.schema.json`'s `triggerDeliveryAttempted.runId` — and that is the MORE load-bearing of the two sites, because `triggerDeliveryAttempted` is a durable event-log payload that rides replay and `:fork`, where `trigger-event` is an in-run payload that never reaches the log. Until this entry was rewritten, the register asserted a correction that had not fully landed, which is worse than not claiming one. **Root cause, and the durable half of the fix:** the stale pairing was one of 13 invalid `examples` across 6 v2 schemas — 9 of them ids minted before their kind became tenant-bound — because `scripts/check-v2-schemas.mjs` skipped `examples` entirely. It now validates every root-level example against its own schema, so the next kind-tightening cannot silently re-seed the same defect.

**Conformance-affecting correction on record (2026-09-26, RFC 0111 (b) — a recount the event log cannot support).** RFC 0111 §"Conformance seam", `multi-agent-execution.md` §"Context economy" and `host-sample-test-seams.md` §14 required the harness to read the events named in the transcript-window seam's `eventIds` "and re-compute their token sum in the advertised `tokenCounter` unit". No implementation of the suite could do that: run events are content-free by design, so the event log carries none of the text the host fed the model, and "the token count of an event" was never defined. The scenario that shipped (`context-budget-transcript-bound`) therefore checked only that each id existed and was unique — it could not fail on a wrong `tokenCount`, a non-tail window, or a budget the run never reached (a budget of 10⁹ passed). The correction: the seam response gains `entries[] { eventId, rendered }`, the exact text fed per item, **REQUIRED when `tokenCounter` is `chars`** (the only unit a black-box harness can recount — Unicode code points, as the schema's "characters" already said) and OPTIONAL otherwise; for `o200k_base`, `cl100k_base` and `host-defined` the recount is stated as advertise-and-attest. The recent-tail rule's undefined "eligible" is defined (same `(type, nodeId)` as an event fed that turn), and a full witness requires the budget to have acted in at least one turn (else `partial-witness`). **No host `MUST` moved** — the bound, the tail and the summary rules are unchanged; `entries[]` is test-seam surface only, served in test mode, and additive (the seam is also added to `api/seams-v2.yaml`). No host implements the seam today, so nothing that passed stops passing. Suite 2.41.0 ships the corrected scenarios (both majors) and the live fixture `conformance-context-budget-live`, because the scripted `conformance-context-budget-multiturn` drives a mock supervisor that RFC 0111 §Scope forbids from advertising `contextBudget`.

**Conformance-affecting correction on record (2026-09-20, openwop#1367 — the v2 bare pack-manifest `signing` block and `FragmentNode.config`).** Seven `schemas/v2/*-pack-manifest.schema.json` files described a `signing` block (`{ publicKeyRef, signatureRef, method }`, or none) that `spec/v2/core/packs.md` §Signing, RFC 0177 §C.3 and migration row `openwop.migration.C10.1` had already replaced with `{ keyId, scheme }`, and `workflow-chain-pack-manifest`'s `FragmentNode.config` was closed by the v1→v2 seed against its own description. The schemas were the outlier on both counts: 0 of 190 published v2 `pack.json` documents validated, and the registry, the prose and the `Accepted` RFC agreed with each other. Corrected in 2.32.0 under RFC 0177; `signing` remains OPTIONAL on a bare manifest, so no previously-valid unsigned document is invalidated. A document carrying the v1 block was never a valid v2 document under the prose, and none is published.

**Conformance-affecting correction on record (2026-09-06, the fork-prefix bracket — `[0, fromSeq]` → `[0, fromSeq)`).** The replay byte-equivalence clause stated its range with a closed upper bracket in both `spec/v1/replay.md` §Determinism guarantees and `spec/v2/core/replay.md` §"Byte-equivalence of the prefix", making the event AT `fromSeq` part of the range that MUST be byte-equivalent between source and replay. Every other statement of the boundary in the corpus is half-open: `replay.md` §The surface and its host algorithm, `runs.md` §Fork, RFC 0036 §E ("the projected event log **up to** `fromSeq`"), and — decisively — the clause's own section heading, which scopes it to *the prefix*, a term the same document defines 23 lines earlier as `sequence < fromSeq`. **The closed bracket was never jointly satisfiable with §Divergence**, which requires a host to *continue* and emit `replay.diverged` when a replayed node produces an event different from the source at the same sequence: the inclusive reading demanded byte-equivalence of an event the very next section permits to differ. **W3C Process Class 3**, on the same reasoning as the RFC 0057 §D and `a2a-push-egress-ssrf` entries above. No `MUST` moved, no shape, code or status changed, and nothing that was conforming stops being so — a host inheriting `[0, fromSeq]` contradicted four other statements and was never conforming; the corpus now says so unambiguously. Not a §2.2 break and **not** a §3 safety-fix. **Origin:** the bracket enters the corpus at RFC 0041 §C and propagated from there to both spec documents and to RFC 0068 §"Replay determinism through a consolidation pass"; the RFCs are left as the historical record of their decisions and are not retroactively edited. **A tier-1 host shipped `sequence <= fromSeq`** — exactly what the closed bracket licensed — and passed every unaided major-2 scenario, finding it only when a *second* defect (1-based sequence numbering) stopped cancelling it. Two errors cancelling is why an instrument, and not a review, is what closes this class; the instrument is `v2-run-fork-prefix` (suite `2.0.0-rc.60`), which asserts the half-open boundary directly. **Known residue, recorded rather than closed:** that scenario compares inherited rows by `sequence` and `type` only, so the *byte*-equivalence this clause requires is still unwitnessed at the payload level, and clause 2's per-index snapshot claim has no unaided witness at all — `GET /runs/{runId}` serves the snapshot at head only, and `diffRun`'s `stateDiff` is terminal state computed by the host under test.

**Conformance-affecting correction on record (2026-09-22, `a2a-integration.md` / `rest-endpoints.md` — A2A fields and a card path that do not exist upstream).** Three statements in the v1 A2A composition named upstream surface that A2A does not define. (1) `a2a-integration.md` §"Operational mapping table", row "Failure on the OpenWOP side mid-run", required that the bridge **MUST** surface `Task.error.message`; the A2A `Task` message is `{ id, contextId, status, artifacts, history, metadata }` in both 0.3 and 1.0.0 (`specification/a2a.proto` at `v1.0.0`) and has no `error` field, so **no implementation could satisfy the MUST**. It now names `Task.status.message` — an agent-role `Message` derived from `RunSnapshot.error.message`, content-free — and the typed code's carrier is spelled `metadata.openwop.error.code`, the `run.failed` carrier the same document already uses in §3 and §"What OpenWOP does NOT specify", replacing a third spelling (`metadata.openwop.errorCode`) that appeared nowhere else. (2) The "Time-skew" row cited `Task.createdAt`, which likewise does not exist; it now cites `Task.status.timestamp`, the only timestamp A2A carries. (3) `rest-endpoints.md` §"A2A" placed the agent card at `/v1/a2a/agent.json` inside a MUST paragraph, contradicting `a2a-integration.md` §A (the A2A well-known path `/.well-known/agent-card.json`, unchanged in 1.0) and the `capabilities.a2a.agentCardUrl` schema description; it now defers to `agentCardUrl`, names the well-known path as canonical, and keeps the mount path as a MAY. **W3C Process Class 3**, on the same reasoning as the `trigger-event.deliveryId` entry above: nothing that was conforming stops conforming, because conforming to (1) was impossible and (3) contradicted the document it composes with; a host that followed the upstream shape was the conforming one. No schema, error code, HTTP status, or scenario changed — no scenario reads `Task.error`, `Task.createdAt`, or `/v1/a2a/agent.json` — so this is not a §2.2 break and **not** a §3 safety-fix. Not corrected here, and recorded so the gap is visible: the A2A **1.0.1** re-mapping of six gRPC/HTTP+JSON error statuses (§D.7; JSON-RPC unchanged) and the message-to-terminal-task error (§D.2) change a normative error mapping and are a separate correction, recorded in the next entry.

**Conformance-affecting correction on record (2026-09-22, `a2a-integration.md` §B/§D — the A2A error table re-pinned to 1.0.1, and a message to a terminal task).** (1) The `a2a-1.0` profile pinned its error table to **A2A 1.0.0**. Upstream **A2A 1.0.1** (released 2026-05-28; `docs/specification.md` §5.4 at tag `v1.0.1`, a2aproject/A2A#1627 "recent transcoding-related error changes") corrected its own table in a patch release. Six gRPC or HTTP+JSON statuses moved: `TaskNotCancelableError` HTTP `409`→`400`; `PushNotificationNotSupportedError`, `UnsupportedOperationError` and `VersionNotSupportedError` gRPC `UNIMPLEMENTED`→`FAILED_PRECONDITION`; `ContentTypeNotSupportedError` HTTP `415`→`400`; `InvalidAgentResponseError` HTTP `502`→`500`. §B, D.6 and D.7 now carry the 1.0.1 statuses, at **SHOULD** for a host acting as server. A host acting as client **MUST** accept either table and **MUST** identify the error by its JSON-RPC code or `ErrorInfo.reason`, never by status alone. The **JSON-RPC codes did not change**, so the mandatory JSON-RPC floor did not move. **Why this is not a §2.2 break.** Each error keeps its meaning; only upstream's binding status moved. The corpus pinned "A2A 1.0", and upstream says a patch number "MUST not be considered" in negotiation, so two conforming `1.0` peers could already disagree. And a host that emits the 1.0.0 statuses stays conforming for the rest of v1.x. The client-side tolerance MUST is additive under §4 ("new normative requirement on a previously-undefined behavior"). (2) §D.2 answered a message to a **terminal** task with `TaskNotFoundError` "per upstream", but upstream §3.1.1 and §3.1.2 name `UnsupportedOperationError` for exactly that case. The corrected rule: a terminal task the caller can still read with `GetTask` ⇒ `UnsupportedOperationError` (**MUST**); a purged or unknown task ⇒ `TaskNotFoundError` (upstream §3.3.2, "already completed and purged"); a task the caller cannot read ⇒ `TaskNotFoundError` whatever its state (§E). **W3C Process Class 3** on the same reasoning as the `trigger-event.deliveryId` entry above. A host following the old text contradicted the upstream MUST that the `a2a-1.0` profile exists to implement, so it was not a conforming A2A 1.0 agent. The reference host (openwop-app, `a2aServer10.ts`) already returns `UNSUPPORTED_OPERATION` for any readable task. Not a §3 safety-fix. **No scenario changed.** None asserts a moved status: `a2a-1-0-agent-card.test.ts` asserts JSON-RPC codes plus VNS HTTP `400`, which did not change, and the suite's fake peer is JSON-RPC-only. None asserts the terminal-`SendMessage` case either: `a2a-1-0-task-roundtrip.test.ts` covers only unknown or unreadable ids. A negative leg for the terminal case belongs to a later suite minor.

**Conformance-affecting correction on record (2026-09-22, OIDC `aud` — a MUST restated as a SHOULD).** `auth-profiles.md` §`openwop-auth-oidc-user-bearer` required the host to "MUST verify the standard OIDC ID-token claims: `iss`, `aud`, …" and, three bullets later, said the host "SHOULD respect `aud` restrictions and reject tokens whose audience does not include the host's configured audience identifier". The second bullet is a weaker restatement of the first, and a reader could take it as permission to accept a wrong-audience token. The two are merged into one requirement: the host MUST reject a token whose `aud` does not include its configured audience identifier, with `401 unauthenticated`; the SHOULD bullet is removed, and the failure-mode list names wrong audience beside wrong issuer. The `openwop-auth-oauth2-client-credentials` section now states the `401 unauthenticated` response for the wrong-audience case it already listed. It does **not** require `aud` to be present, since opaque or introspected tokens may carry none. **W3C Process Class 3**, on the same reasoning as the RFC 0057 §D entry above: a host that read the SHOULD as permission was already violating the MUST, so its conformance was unclear and is now clearly non-conforming. No `MUST` moved and no shape, code or status changed. The requirement registry already recorded `openwop.it.auth-oidc-user-bearer.wrong-aud-401` as a MUST, v2 already requires the audience check (`spec/v2/core/identity.md`), and the v1 code stays `unauthenticated` (v2's `audience_mismatch` is not imported). This is not a §2.2 break and **not** a §3 safety-fix. The ID-token allowance (`id-token-or-access-token`) is untouched. **Evidence, and its limit:** before the change, every host in the INTEROP matrix was checked for wrong-audience handling. The postgres example host (`jwt-validator.ts`) and openwop-app (`oidcVerifier.ts`; its own `auth-oidc.test.ts` wrong-audience → 401 leg passes) both reject by source, and neither falls through to acceptance. The sqlite and in-memory example hosts and MyndHyve do not advertise the profile. The `auth-oidc-user-bearer` wrong-aud leg is harness-gated on `OPENWOP_TEST_OIDC_ISSUER_URL` and is not strict-executed in any committed bundle, so this rests on source inspection and a host-side test, not on a witnessed suite run.

**Conformance-affecting correction on record (2026-09-22, `suspend-request` — an interrupt `data` union not bound to its `kind`).** `schemas/suspend-request.schema.json` and `schemas/v2/suspend-request.schema.json` typed `InterruptPayload.data` as a `oneOf` over the eight per-kind shapes without tying any branch to `kind`. `ConversationStartData` (`{ conversationId, title?, initialPrompt? }`) and `ConversationCloseData` (`{ conversationId, reason? }`) are both satisfied by `{ conversationId }`, so the minimal `conversation.start` and `conversation.close` payloads that `spec/v1/interrupt.md` and `spec/v2/core/interrupt.md` §Per-kind payloads define matched two branches and **failed validation in both v1 and v2** — a host emitting the shape the prose requires was refused by the contract; `interrupt.requested` inherits the defect through its `$ref`. The same unbound union **accepted a payload whose `data` belonged to another kind** (`kind:"approval"` carrying `ClarificationData`, `kind:"low-confidence"` carrying `CustomData`), which the prose's per-kind table never permitted. The union is now an `anyOf` and the root `allOf` binds each `kind` to exactly its own shape (one `if`/`then` per kind). No per-kind shape changed, so nothing the prose permits is narrowed: every payload whose `data` matches its own kind's shape validates as before, the two minimal conversation payloads now validate, and only mismatched kind/data pairs — never conforming under the prose — are refused. **W3C Process Class 3**, on the same reasoning as the `trigger-event.deliveryId` entry above: conforming to the prose was impossible for two kinds, and the accepted mismatches were never conforming. No `$id`, `kind`, field, or `MUST` moved, so this is not a §2.2 break and **not** a §3 safety-fix. Witnessed by `conformance/fixtures/interrupt-payloads/` (one minimal positive per kind, five mismatched negatives, each negative's `data` checked valid under its own kind so it fails only for the binding) in `fixtures-valid.test.ts`, suite 2.36.0; with the binding reverted, the positive `conversation.start` and `conversation.close` fixtures are refused and four of the five negatives are accepted (sabotage-checked). Found by ajv probe in the 2026-09 MCP/A2A review (P3-H7), ahead of the RFC that adds an authorization interrupt kind, which would otherwise have widened the ambiguity.

**Conformance-affecting correction on record (2026-09-23, RFC 0214 — an A2A push credential is a destination credential).** `spec/v2/core/security-defaults.md` §"Onward hops" forbade attaching "credential material carried in a body" to any outbound request, A2A included, and allowed only "credentials the host holds for that destination". An A2A `CreateTaskPushNotificationConfig` carries its `authentication.credentials` and `token` in the request body, and A2A v1.0.1 §4.3.3 requires the agent to send them on every push; the interop map already required the host to hold them by reference. The two rules could not both be satisfied by any host advertising `a2a.pushNotifications`. The corrected text names the push credential a destination credential — sent only to the registered push URL's origin, never after a redirect, discarded on delete or the final push — and makes it the one, narrower, exception. **W3C Process Class 3**: the prior text had no satisfiable reading for a push-advertising host, so no host could have conformed to it. **Census:** 0 of 3 committed v2 bundles advertise `a2a.pushNotifications: true`. No schema pointer moved (two `a2a-task-state` descriptions were corrected, including the address-only abbreviation of the SSRF guard that the 2026-08-25 entry fixed in v1 but not in this v2 description), so there is no `spec/v2/corrections.json` row. Not a §2.2 break and not a §3 safety-fix. RFC 0214 §B–§E add push delivery rules, additive and gated on the same facet.
**Evidence correction on record (2026-09-23, `openwop.requirement.0175.negotiation-authenticated` — an acceptance row that measured the harness, and a clause no bundle has exercised).** RFC 0175 §D.1 requires that an **unauthenticated** negotiation exchange MUST NOT land below the host's `preferredVersion`. Two suite legs mint it, and both are `executed-pass` in the committed reference-host bundle (suite 2.35.0, build `commit:8477d75f`, witness `5562d7c57609…`). **The MCP row measured nothing about the host.** The leg constructs a single-era `McpFakeServer(['2025-06-18'])` on an ephemeral port and hands the host `hostFacingEndpoint()`; since suite 2.33.0 that resolves to `OPENWOP_MCP_FAKE_SERVER_URL`, the operator's public front, which forwards to the **pinned** port the shared setup-level fake server owns — a dual-era server speaking the preferred revision. `host-sample-test-seams.md` §23 defines no field that makes a server offer *only* a lower revision (`requestVersion` overrides what the host **asks for**, which is §D.2's floor case, and this leg does not pass it), so no lower offer reached the host: it discovered `2026-07-28`, negotiated at it, and the leg asserted `negotiatedVersion === preferredVersion` — a property of the harness, which is the false positive the evidence apparatus exists to prevent. The row's assertion count records the moment it went hollow: **4** in every pre-front cut of this host (2.4.0 through 2.25.0, the 2.4.2 acceptance witness among them), **3** in every cut since the fronts landed in suite 2.33.0; the missing one is the wire leg, which iterates the scenario-owned server's `invocations()` — empty, because the host never reached that instance. The three sibling rows (`minimum-version-refused`, `minimum-version-refused.mcp`, `negotiation-authenticated`) drove the host's refusal decision genuinely through `peerOffersOnly` / `requestVersion`, and each refused as §D.2 requires — but their wire half asserts nothing in the committed bundle either, for two different reasons: the MCP sibling lost its one wire assertion (8 → 7) when the front took the host away from the scenario's own server, and the two A2A legs never had one, because the host refuses before it makes any non-GET call while the leg inspects only non-GET calls (the Agent Card `GET` is filtered out). **What the routing defect hid:** the host refuses as `unauthenticated` only when the negotiated version would land below `preferredVersion` **and** at or above the floor, and the only host that has ever witnessed these ids advertises `preferredVersion` equal to its floor on both protocols, in every one of its cuts — so **no committed bundle, fronted or loopback, has exercised §D.1's authentication clause**; what the genuine rows measured is §D.2's floor rule. **Classification.** The defect is the **suite's**: no host emitted anything it should not have, none is convicted or acquitted here, and no `MUST`, shape, code, status or schema pointer moved — so this is not a §2.2 break, not a §3 safety-fix, and not a W3C Class 2 or Class 3 *spec* correction. It is an **evidence** correction, recorded in this register because an `Accepted` RFC's acceptance tick cited the row. **`spec/v2/corrections.json` does not fit** and no row is added there: that register (RFC 0197 §A.4) requires at least one schema pointer the correction **moved**, plus a prior-shape bundle and registry census, and this correction moves no v2 shape. The harness fix has since landed (openwop#1520, suite 2.37.0): `conformance/src/lib/front-mux.ts` nonce-paths each scenario-owned fake behind the one operator front, so the host now reaches **this** server — the one that offers only `2025-06-18`, which is where the lower offer comes from, §23 still having no knob for it — and both legs now record `blocked` instead of a pass when the seam answers a success and the suite's own peer received no request. Recorded on RFC 0175 (Updated 2026-09-23, **Status unchanged**) and as gaps `openwop.gap.0175.5` (the re-cut owed now that the harness fix has landed) and `openwop.gap.0175.6` (§D.1 needs a host whose floor sits below its preferred version). Until the re-cut lands, the reference host's `INTEROP-MATRIX.md` row discloses that its recorded pass for this requirement predates the fix.

**Conformance-affecting correction on record (2026-09-28, openwop#1706 — pack isolation and manifest rows gated on registry resolution).** `spec/v2/core/packs.md` §"The `packs` capability" says a host MUST NOT advertise `packs` unless it resolves pack references through a registry, and told a client to read an absent record as "this host installs no packs". Four v2 scenarios (`v2-pack-isolation`, `v2-manifest-ceiling-refused`, `v2-manifest-hatch-carried`, `v2-peer-dependency-declared`) gated on that record, and RFC 0173 §B and RFC 0177 §A.1/§B.1/§C.2 named the gate. **A host that loads and sandboxes local packs, and correctly omits `packs`, could not be measured on isolation or manifest enforcement at all.** The v2 reference host lost about 20 rows that way when it dropped a `packs` record it was not entitled to (openwop-examples#108). The absent-record sentence now says what the record claims: no registry resolution, and nothing about validation or execution, which `sandbox` and §"The engine range" bind independently. `v2-pack-isolation` gates on `sandbox` alone. The manifest trio gate on the seams-profile install path, and a publish-seam 404 records `inapplicable` when `packs` is absent and `blocked` when it is advertised. **W3C Process Class 3.** No shape, code, status or requirement id changed. A host that advertises `packs` is measured exactly as before, and a host that omits it is now measured instead of skipped.

**Conformance-affecting correction on record (2026-09-28, openwop#1696 — a timeout never grants an approval gate).** RFC 0093 ruled that an approval gate reaching its timeout MUST resolve rejected, and that auto-approving "fails open and is non-conformant". RFC 0186 §A.3 later seated `ApprovalData.onTimeout` as `reject | approve | escalate` from measured payloads without revisiting that ruling, and RFC 0223 §A defined the timeout only for `onTimeout` absent or `reject`. **The corpus therefore read as permitting a fail-open timeout it had ruled out.** `spec/v2/core/interrupt.md` §Rejection now resolves a timed-out gate rejected whatever `onTimeout` holds. A timeout MUST NOT grant a gate. `approve` is treated as `reject` and SHOULD NOT be emitted, and `escalate` MAY notify a host-defined target but MUST NOT extend or grant the gate. The `onTimeout` enum is unchanged, because recorded payloads carry `approve`; only its description moves.
